2

사용자와 쓰임새

다른 시스템의 명단을 가져온 화면

홈페이지 온라인 예약 신청 명단임. 이 데이터는 대시보드 DB 가 아니라 레거시 PHP 홈페이지의 MariaDB에 있음. 레거시 관리자 화면 counsel/online_list.php 를 조회 전용으로 옮겼음.

쓰는 장면하는 일
온라인 신청 확인홈페이지로 들어온 예약 신청을 봄
UTM · 추천인 확인어느 캠페인에서 왔는지 — CRM 에는 없는 정보임
CRM 대조홈페이지 신청과 CRM 예약수의 차이를 봄
⚠️ 예약자 리스트의 홈페이지 채널과 다른 것임

이 화면 = 홈페이지에 신청한 건(레거시 홈페이지 DB)
예약자 리스트의 '홈페이지' 채널 = CRM 에 예약으로 등록된 건
신청이 곧 예약은 아니라 두 숫자는 다름. 건별 대조 기록이 점검 문서에 있음.

레거시와 의도적으로 다르게 만든 것

항목결정이유
삭제 · 체크박스제외조회 전용으로 옮겼음. 쓰기 액션은 가져오지 않았음
CSV제공다른 리스트와 동일. 개인정보가 원문으로 나감
검색이름 + 휴대폰번호 통합레거시는 휴대폰 검색이 안 돼 운영 불편이 있었음
개인정보화면은 원문 · CSV 는 마스킹다른 명단 화면과 같은 방식임
신선도 배너신규 추가레거시엔 없음 — 아래 참조
필터 UI공통 툴바레거시 4블록 라디오 폼 대신
필터 적용구분·예약구분·검색은 즉시, [조회]는 등록일 재조회 전용—
⚠️ 배너를 지우지 말 것

스냅샷 소스일 때 조회 기간이 스냅샷 범위를 넘으면 에러 없이 건수가 모자라게 나옴. 화면이 마지막 등록일과 비교해 경고 배너를 띄워 이 조용한 실패를 드러냄. 실시간 소스에서는 천장이 없어 같은 비교가 거짓 경고가 되므로 live 플래그로만 끔 — 배너 자체를 지우면 안 됨.

표 · 지표 정의

원천 — 대시보드 밖의 시스템

항목값
DBMariaDB — 레거시 PHP 홈페이지의 운영 DB (bseyecom_db)
테이블TBL_COUNSEL — 7개 상담 채널을 한 테이블에 담음
필터CATEGORY='COUNSELONLINE'(온라인 예약만) · DEL_TF='N'(삭제 제외)
접근내부망, SSH 터널 경유. 앱은 localhost:<터널포트> 로 붙음
설정HOMEPAGE_DATASOURCE_URL 하나로 SQLite 스냅샷 / MariaDB 직결을 URL 접두사로 자동 스위칭
현재 경로 — 배치가 마트에 적재함

지금은 배치가 MariaDB 를 읽어 mart_list_reservation_homepage 에 적재하고 화면은 마트를 조회함. 조회 시점 원본 직결은 더 이상 표준 경로가 아님.
1단계(직결)는 실증용이었고 "운영 실시간이 필요하면 마트 ETL 쪽이 맞다"는 판단대로 2단계로 갔음.

레거시 동작을 그대로 따른 것 — 바꾸면 건수가 틀어짐

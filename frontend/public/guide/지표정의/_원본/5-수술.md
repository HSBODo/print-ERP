# 지표정의 5 — 수술

> 환자 흐름(예약 → 검사 → 전환율/중단율 → **수술** → 외래)의 다섯 번째 단계.
> **무엇으로 이루어지고, 데이터를 어디서 가져오는지**를 정리함.

## 한눈에 보기

**수술은 세 갈래로 나뉨.** 서로 다른 테이블에서 오고, 세는 단위도 다름.

| 구성 | 무엇인가 | 데이터 출처 | 날짜 기준 | 세는 단위 |
|---|---|---|---|---|
| **시력교정수술** | 라식·라섹·스마일·렌즈삽입 등 | `OPERATIONDATA` | `OPERATION_DATE` | **사람** |
| **백내장수술** | 백내장 인공수정체 수술 | `Cataract_Operationdata` | `OPERATIONR_DATE`<br>`OPERATIONL_DATE` | **눈** (좌/우 각각) |
| **재수술** | 이미 수술한 눈을 다시 수술 | `RE_OPERATION` | `REOP_DATE` | **건** |

> ⚠️ **단위가 다르므로 단순히 더하면 안 됨.** 시력교정은 사람, 백내장은 눈임.
> 총 수술수 = 시력교정 **사람** + 백내장 **눈** + 재수술 **건**
> (2026-07 실측: 784 + 45 + 32 = **861**).
>
> 같은 사람·같은 날이 수술과 재수술에 각각 잡히는 중복이 있으나(렌즈 제거+삽입처럼 한 세션이
> 두 테이블에 기록된 경우) 레거시도 같은 방식으로 더하므로 걸러내지 않음 — 확정된 정의임.

## 데이터 흐름 — 뷰 하나에서 갈라짐 (2026-08-06~)

```
list_surgery(시력교정·백내장) + list_reoperation(재수술)
      └─ v_all_surgery_list (V37, 눈 단위 전개 + 유형 분류)
            └─ select-surgery-daily-agg.sql (일별)
                  ├─ 월로 접기   → SurgeryMartJob  → 월간 레포트·수술 건수·주요 수술별 비중
                  └─ ISO 주차로  → WeeklyReportService → 주차 레포트·수술별 비중
```

종전에는 같은 지표를 MSSQL 쿼리 **4벌**(시력교정 월별/일별 · 백내장 월별/일별)이 각자 구현했고,
주석에 *"둘은 같은 기준이어야 한다"* 고 사람이 지켜야 할 규약으로만 적혀 있었음.
실제로 어긋났음 — **2026-06 백내장이 리스트 62 vs 집계 65**.

**화면 원칙** — 리스트 행은 **사람**, 표시 숫자는 **안**.
수술자 리스트는 사람 목록이라 6월에 62행이지만, 백내장 수술수는 65안이 맞음.
뷰가 눈 단위로 펼쳐 두고 집계에서 갈라 씀.

| 지표 | 집계식 |
|---|---|
| 시력교정 수술수 | `COUNT(DISTINCT patient_key)` — 사람×수술일 |
| 백내장 수술수 | `COUNT(*)` — 안 |
| 재수술 | `COUNT(*) WHERE included` — 건 |

> ⚠️ **적용 구간은 2026-06 부터임.** `SurgeryMartJob.MART_LIVE_FROM = 2026-06-01` 가드가
> 그 이전을 확정값으로 보호함 — 2024·2025 는 `V15`, 2026-01~05 는 `V35` 시드가 정본임.
> 정의를 바꿔도 앞 구간 숫자는 움직이지 않음.
>
> 🙈 그래서 **2026-02 시력교정 리스트 1386 vs 월별 1388(+2)** 은 원인 미규명 상태로 얼어 있음.
> 나중에 어느 쪽이 맞는지 가려지면 `V35` 시드를 고치면 됨.

> ⚠️⚠️ **뷰의 패턴 매칭은 `ILIKE` 로 씀(`LIKE` 아님).**
> 원본 MSSQL 의 DB collation 이 `Korean_Wansung_CI_AS` = **대소문자 무시**라 거기서는
> `LIKE` 가 이미 CI 로 동작함. Postgres `LIKE` 는 CS 라 그대로 옮기면 분류가 갈림.
> 실제로 겪었음 — `T-Tecnis Puresee`(소문자 s)가 `%PureSee%` 에 안 걸려
> catEdof 대신 catMono 로 떨어졌음(2026-07 EDOF 22→21, Mono 2→3).
> 시술명은 수기 입력이라 대소문자가 제각각이므로 CI 가 맞음.

> 📌 **재수술 포함/제외 판정은 마트에 굳히지 않음.** `reoperation_decision`(JPA 표)을
> 뷰가 조회 시점에 `LEFT JOIN` 하므로, 화면에서 판정을 고치면 배치 없이 즉시 반영됨.
> 반면 렌즈/레이저 구분(`is_lens`)은 적재 시점에 자바가 계산해 넣음 —
> 시술명 패턴의 SSOT 는 `ReoperationOverlay.LENS_PATTERNS` 한 곳임.

**공통 규칙 — 세 갈래 모두 적용**

- 예약일이 아니라 **실제 수술한 날** 기준
- 고객명에 `테스트`·`test`가 들어가면 제외
- 수술명이 비어 있거나 `X`·`OP불가`·`모든수술가능`·`op x`·`Strabismus`·`TEST-TEST`면 제외

| 항목 | 내용 |
|---|---|
| **무엇을 세나** | 그 기간에 시력교정 수술을 실제로 받은 **사람 수** |
| **테이블** | `OPERATIONDATA` (고객당 1행) |
| **날짜** | `OPERATION_DATE` |
| **수술명** | `OPERATIONR`(오른눈) · `OPERATIONL`(왼눈) |
| **단위** | 사람 = `COUNT(DISTINCT CUST_NUM)` |
| **화면** | `/stats/surgery` 수술 건수 · `/stats/surgery-ratio` 주요 수술별 비중 |

### 무엇으로 이루어지나 — 수술 유형 10종

`OPERATIONR`/`OPERATIONL`에 적힌 **수술명 문자열을 보고** 분류함.

| 유형 | 매칭 키워드 |
|---|---|
| 프레스비욘드 `presbyond` | `PRESBYOND` |
| 스마일프로 `smilePro` | `SMILE Pro` · `SMILEpro` · `SMILE PRO` |
| 스마일 `smile` | `SMILE` |
| 비바 `viva` | `VIVA` |
| T-ICL `tIcl` | `T-ICL` · `T-IPCL` · `T-GLAZE` · `T-ECHO` |
| ICL `icl` | `ICL` · `IPCL` · `ARF` · `ART` · `ARTIFLEX` · `GLAZE` · `ECHO` |
| T-KPL `tKpl` | `T-KPL` |
| KPL `kpl` | `KPL` |
| 라식 `lasik` | `FLAP LIFT` · `OPTI` · `iFS` · `VISU` · `fs200` · `Micro+` · `Hybrid` |
| 라섹 `lasek` | `EYECLE` · `T-prk` · `EYE CLE` · `EYE+` · `FLAP PRK` · `PtK` · `M-LE` |

> **위에서부터 순서대로** 판정함. `SMILE Pro`가 `SMILE`보다 먼저 걸리도록 순서가 중요함.
> `PRESBYOND`를 맨 앞에 둔 이유는 `Mono+PRESBYOND` 처럼 다른 표기와 섞여 들어와도 노안 시술로
> 잡아야 하기 때문임(2026-08-05 신설 — 이전에는 분기가 없어 `other`로 빠졌음).
> 어디에도 안 걸리면 `other`가 되고 유형별 집계에서 빠짐. **신규 수술명이 생기면 여기에 추가해야 함.**

### ⚠️ PIOL 유형별은 "대표유형" 하나만 셈

**PIOL 5종(`icl`·`tIcl`·`kpl`·`tKpl`·`viva`)에만 적용되는 예외 규칙임.**

| | 규칙 |
|---|---|
| 대표유형 | **우안(`OPERATIONR`) 우선.** 우안에 PIOL 이 없으면 좌안(`OPERATIONL`) |
| 집계 단위 | 환자 × 집계버킷(일별=일자, 월별=연·월)당 **한 유형에만** 1 |
| 적용 범위 | PIOL 5종만. 라식·라섹·스마일·부가옵션은 종전대로 받은 항목마다 셈 |

**왜.** 양안에 서로 다른 렌즈를 넣는 경우가 흔함(오른눈 ICL · 왼눈 T-ICL).
받은 유형마다 세면 한 사람이 두 칸에 잡혀 **유형별 합이 실제 환자 수보다 커짐.**

**근거.** 레거시 월간보고와 대조해 역산했음. 2026-07 혼합 환자 20명 전원이 우안 기준으로
배정할 때 예외 없이 재현됨.

| | 받은 유형마다(옛 방식) | 대표유형(현행) | 레거시 월간보고 |
|---|---:|---:|---:|
| ICL | 44 | **41** | 41 |
| T-ICL | 76 | **68** | 68 |
| KPL | 19 | **16** | 16 |
| T-KPL | 28 | **22** | 22 |
| VIVA | 1 | **1** | 2 ← 레거시 오분류 |
| 합계 | 168 (합) / 148 (실인원) | **148** | 149 |

레거시 VIVA 2 는 백내장 환자 1명의 `Clareon Vivity` 를 `VIVA` 로 본 오분류임(우리 1이 맞음).
그 1명 때문에 시력교정 총계도 레거시 785 vs 우리 784 로 갈림.

> 그래서 **PIOL 만은 "유형별 합 = 합계"가 성립함.** 아래 함정 ①의 예외임.

### 부가 옵션 5종 (유형과 별개로 중복 집계)

| 옵션 | 매칭 |
|---|---|
| 엑스트라 `xtra` | `+X` |
| 웨이브비전 `waveVision` | `W.V` |
| 모노비전 `monoVision` | `MONO`로 시작 |
| 콘트라 `contra` | `CONT` |
| 퍼스널 `personal` | `P.E` |
| 라섹 EX500 / RED | `EYECLE` + `EX500` / `EYECLE` + `RED` |

### 쿼리 (핵심만)

```sql
-- 좌우 눈을 UNION ALL 로 펼친 뒤 사람 단위로 DISTINCT
SELECT YEAR(op_date) AS yr, MONTH(op_date) AS mo,
       COUNT(DISTINCT CASE WHEN op_type='smile' THEN cust_num END) AS smile,
       -- ... 유형별 반복 ...
       COUNT(DISTINCT cust_num) AS visionPatients
FROM (
    SELECT o.OPERATION_DATE AS op_date, o.CUST_NUM AS cust_num,
           o.OPERATIONR AS raw, <위 분류 CASE> AS op_type
    FROM OPERATIONDATA o WITH(NOLOCK)
    LEFT JOIN CUSTOM cu WITH(NOLOCK) ON cu.CUST_NUM = o.CUST_NUM
    WHERE o.OPERATION_DATE >= :from AND o.OPERATION_DATE <= :to
      AND o.OPERATIONR IS NOT NULL AND RTRIM(o.OPERATIONR) <> ''
      AND o.OPERATIONR NOT IN ('X','OP불가','모든수술가능','op x','Strabismus','TEST-TEST')
      AND NOT EXISTS (SELECT 1 FROM Cataract_Operationdata co WITH(NOLOCK)
                      WHERE co.CUST_NUM = o.CUST_NUM)      -- ★ 백내장 고객 제외
      AND NOT (테스트 고객)
    UNION ALL
    <OPERATIONL 로 같은 블록 반복>
) e
GROUP BY YEAR(op_date), MONTH(op_date)
```

> ⚠️ **`NOT EXISTS Cataract_Operationdata`가 중요함.** 백내장 수술 이력이 있는 고객은
> **기간과 무관하게 통째로 빠짐.** 백내장 수술을 받은 분이 나중에 시력교정 수술을 받아도 안 잡힘.
> 백내장/시력교정 중복 집계를 막으려는 장치지만, 부작용이 있다는 점을 알고 있어야 함.

## 2. 백내장수술

| 항목 | 내용 |
|---|---|
| **무엇을 세나** | 그 기간에 백내장 수술을 받은 **눈 수** |
| **테이블** | `Cataract_Operationdata` |
| **날짜** | `OPERATIONR_DATE`(오른눈) · `OPERATIONL_DATE`(왼눈) — **눈마다 날짜가 다름** |
| **수술명** | `OPERATIONR` · `OPERATIONL` (인공수정체 종류) |
| **단위** | 눈 = `고객번호 + 수술일 + R/L` 조합 |
| **화면** | `/stats/surgery` · `/stats/surgery-composition` |
| **쿼리** | [select-cataract-monthly-by-type.sql](../../../backend/src/main/resources/sql/softcrm/surgery/select-cataract-monthly-by-type.sql) |

> **왜 눈 단위인가** — 백내장은 좌우를 **다른 날 수술하는 경우가 많음.** 그래서 눈마다 수술일이 따로 있고,
> 레거시 백내장 수술건수도 눈 기준이라 그에 맞췄음.

### 무엇으로 이루어지나 — 인공수정체 3종

| 유형 | 매칭 키워드 |
|---|---|
| EDOF `catEdof` | `EDOF` · `Vivity` · `Eyhance` · `PureSee` · `Isopure` · `Symfony` |
| 다초점 `catMulti` | `Clareon` · `Panoptix` · `RESTOR` · `Lara` · `LISA` · `CTR(M)` · `CTRmulti` · `3PodF` · `T-CTR` · `T-CATARACT` · `Precizon` · `LAL` · `ELANA` · `Gemetric` |
| 단초점 `catMono` | `K-flex` · `Kflex` · **그 외 전부** |

> ⚠️ **단초점이 기본값(`ELSE`)임.** 새 다초점 렌즈명이 등장하면 조용히 단초점으로 잡힘.
> 신제품 도입 시 목록 갱신이 필요함.

> ✅ **`T-Clareon Vivity` 는 EDOF(프리미엄)다 — 2026-08-05 확정.**
> 이름에 `Clareon`(다초점)과 `Vivity`(EDOF)가 둘 다 들어 있어 CASE 순서에 따라 갈리는데,
> **EDOF 를 먼저 보는 현재 순서가 맞음.** 의학적으로 Vivity 는 EDOF 이고, 레거시 월간보고가
> `Clareon` 계열을 통째로 다초점으로 묶은 쪽이 어긋난 것임.
> **레거시 PDF 에 맞추려고 CASE 순서를 뒤집지 말 것** (2026-06 다초점 36 vs PDF 33,
> 2026-07 프리미엄 22 vs PDF 21 — 이 차이는 정상임).

### 쿼리 (핵심만)

```sql
SELECT YEAR(op_date) AS yr, MONTH(op_date) AS mo,
       COUNT(DISTINCT CASE WHEN cat_type='catMulti' THEN eye_key END) AS catMulti,
       COUNT(DISTINCT CASE WHEN cat_type='catMono'  THEN eye_key END) AS catMono,
       COUNT(DISTINCT CASE WHEN cat_type='catEdof'  THEN eye_key END) AS catEdof,
       COUNT(DISTINCT eye_key) AS cataractPatients
FROM (
    SELECT c.OPERATIONR_DATE AS op_date,
           LTRIM(RTRIM(c.CUST_NUM)) + '|' + c.OPERATIONR_DATE + '|R' AS eye_key,   -- ★ 눈 키
           <분류 CASE> AS cat_type
    FROM Cataract_Operationdata c WITH(NOLOCK)
    WHERE c.OPERATIONR_DATE >= :from AND c.OPERATIONR_DATE <= :to
      AND c.OPERATIONR IS NOT NULL AND RTRIM(c.OPERATIONR) <> ''
      AND c.OPERATIONR NOT IN ('X','OP불가','TEST-TEST')
      AND NOT (테스트 고객)
    UNION ALL
    <OPERATIONL / OPERATIONL_DATE 로 같은 블록 반복, eye_key 는 '|L'>
) e
GROUP BY YEAR(op_date), MONTH(op_date)
```

## 4. 알아둬야 할 함정

### ① 유형별 합계 ≠ 전체 인원 (단, PIOL 은 예외)

**양쪽 눈에 다른 수술을 할 수 있음.** 오른눈 스마일 · 왼눈 라섹이면 `smile`에도 `lasek`에도 1명씩 잡히지만
전체 인원(`visionPatients`)은 1명임. **유형별 숫자를 더해서 전체와 맞추려 하면 안 됨.**

> **예외 — PIOL 5종.** 2026-08-05부터 대표유형(우안 우선) 하나에만 집계하므로
> `icl+tIcl+kpl+tKpl+viva` = `piolPatients` 가 성립함(위 §PIOL 대표유형 참조).
> 반대로 **PIOL 유형별 값은 "그 렌즈를 받은 사람 수"가 아님** — 양안에 다른 렌즈를 넣으면
> 우안 쪽에만 잡히므로 실제 시술 건수보다 작음(2026-07 ICL: 실제 44명 시술 / 대표유형 41명).

### ② 시력교정에서 백내장 고객이 통째로 빠짐

`NOT EXISTS Cataract_Operationdata`가 **기간 제한 없이** 걸려 있음.
2020년에 백내장 수술을 받은 분이 2026년에 시력교정 수술을 받아도 시력교정수술에 안 잡힘.

### ③ 수술명 문자열 매칭이라 신규 수술명에 취약함

세 갈래 모두 **수술명 텍스트를 `LIKE`로 훑어** 분류함.
새 수술명·새 렌즈명이 도입되면 조용히 `other`(시력교정)나 `단초점`(백내장)으로 흘러감.
**신규 수술 도입 시 분류 목록 갱신이 필요함.**

### ④ 재수술 판정 — ✅ 2026-07-31 `REASON_CD` 기반으로 전환 완료

> **아래 서술은 전환 전 기록임.** 2026-07-31 에 `01`·`07`·`10` 제외 + 시술명 `Irrigation` 보정
> 규칙으로 SQL 3개 파일에 반영됐음. 전환 후 2026 월별 실측: 01=32 · 02=33 · 03=18 · 04=19 ·
> 05=23 · 06=17 · 07=31. **비교연도도 함께 바뀌었음**(2024 213→205 · 2025 279→272).
> 렌즈/레이저 분류도 행 단위 판정으로 바뀌어 2026 렌즈 103→105.
> ⚠️ 마트를 읽는 화면이라 **SURGERY 도메인 재적재를 해야 반영됨.**
> 상세·승인 범위: [재수술-분류_2026-01~07.md](../../점검/재수술-분류_2026-01~07.md) §적용 기록.
>
> 단, **사유코드에도 오입력이 있어** 시술명 보정을 함께 씀 — 순수 `REASON_CD` 단독 판정이 아님.

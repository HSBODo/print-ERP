지표정의 5 — 수술

환자 흐름(예약 → 검사 → 전환율/중단율 → 수술 → 외래)의 다섯 번째 단계. 무엇으로 이루어지고, 데이터를 어디서 가져오는지를 정리함.

한눈에 보기

수술은 세 갈래로 나뉨. 서로 다른 테이블에서 오고, 세는 단위도 다름.

⚠️ 단위가 다르므로 단순히 더하면 안 됨. 시력교정은 사람, 백내장은 눈임. 총 수술수 = 시력교정 사람 + 백내장 눈 + 재수술 건 (2026-07 실측: 784 + 45 + 32 = 861).

같은 사람·같은 날이 수술과 재수술에 각각 잡히는 중복이 있으나(렌즈 제거+삽입처럼 한 세션이 두 테이블에 기록된 경우) 레거시도 같은 방식으로 더하므로 걸러내지 않음 — 확정된 정의임.

데이터 흐름 — 뷰 하나에서 갈라짐 (2026-08-06~)

list_surgery(시력교정·백내장) + list_reoperation(재수술)
      └─ v_all_surgery_list (V37, 눈 단위 전개 + 유형 분류)
            └─ select-surgery-daily-agg.sql (일별)
                  ├─ 월로 접기   → SurgeryMartJob  → 월간 레포트·수술 건수·주요 수술별 비중
                  └─ ISO 주차로  → WeeklyReportService → 주차 레포트·수술별 비중

종전에는 같은 지표를 MSSQL 쿼리 4벌(시력교정 월별/일별 · 백내장 월별/일별)이 각자 구현했고, 주석에 "둘은 같은 기준이어야 한다" 고 사람이 지켜야 할 규약으로만 적혀 있었음. 실제로 어긋났음 — 2026-06 백내장이 리스트 62 vs 집계 65.

화면 원칙 — 리스트 행은 사람, 표시 숫자는 안. 수술자 리스트는 사람 목록이라 6월에 62행이지만, 백내장 수술수는 65안이 맞음. 뷰가 눈 단위로 펼쳐 두고 집계에서 갈라 씀.

지표집계식
시력교정 수술수COUNT(DISTINCT patient_key) — 사람×수술일
백내장 수술수COUNT(*) — 안
재수술COUNT(*) WHERE included — 건

⚠️ 적용 구간은 2026-06 부터임. SurgeryMartJob.MART_LIVE_FROM = 2026-06-01 가드가 그 이전을 확정값으로 보호함 — 2024·2025 는 V15, 2026-01~05 는 V35 시드가 정본임. 정의를 바꿔도 앞 구간 숫자는 움직이지 않음.

🙈 그래서 2026-02 시력교정 리스트 1386 vs 월별 1388(+2) 은 원인 미규명 상태로 얼어 있음. 나중에 어느 쪽이 맞는지 가려지면 V35 시드를 고치면 됨.

⚠️⚠️ 뷰의 패턴 매칭은 ILIKE 로 씀(LIKE 아님). 원본 MSSQL 의 DB collation 이 Korean_Wansung_CI_AS = 대소문자 무시라 거기서는 LIKE 가 이미 CI 로 동작함. Postgres LIKE 는 CS 라 그대로 옮기면 분류가 갈림. 실제로 겪었음 — T-Tecnis Puresee(소문자 s)가 %PureSee% 에 안 걸려 catEdof 대신 catMono 로 떨어졌음(2026-07 EDOF 22→21, Mono 2→3). 시술명은 수기 입력이라 대소문자가 제각각이므로 CI 가 맞음.

📌 재수술 포함/제외 판정은 마트에 굳히지 않음. reoperation_decision(JPA 표)을 뷰가 조회 시점에 LEFT JOIN 하므로, 화면에서 판정을 고치면 배치 없이 즉시 반영됨. 반면 렌즈/레이저 구분(is_lens)은 적재 시점에 자바가 계산해 넣음 — 시술명 패턴의 SSOT 는 ReoperationOverlay.LENS_PATTERNS 한 곳임.

쿼리 (핵심만)

-- 좌우 눈을 UNION ALL 로 펼친 뒤 사람 단위로 DISTINCT
SELECT YEAR(op_date) AS yr, MONTH(op_date) AS mo,
       COUNT(DISTINCT CASE WHEN op_type='smile' THEN cust_num END) AS smile,
       -- ... 유형별 반복 ...
       COUNT(DISTINCT cust_num) AS visionPatients
FROM (
    SELECT o.OPERATION_DATE AS op_date, o.CUST_NUM AS cust_num,
           o.OPERATIONR AS raw, <위 분류 CASE> AS op_type
    FROM OPERATIONDATA o WITH(NOLOCK)
    LEFT JOIN CUSTOM cu WITH(NOLOCK) ON cu.CUST_NUM = o.CUST_NUM
    WHERE o.OPERATION_DATE >= :from AND o.OPERATION_DATE <= :to
      AND o.OPERATIONR IS NOT NULL AND RTRIM(o.OPERATIONR) <> ''
      AND o.OPERATIONR NOT IN ('X','OP불가','모든수술가능','op x','Strabismus','TEST-TEST')
      AND NOT EXISTS (SELECT 1 FROM Cataract_Operationdata co WITH(NOLOCK)
                      WHERE co.CUST_NUM = o.CUST_NUM)      -- ★ 백내장 고객 제외
      AND NOT (테스트 고객)
    UNION ALL
    <OPERATIONL 로 같은 블록 반복>
) e
GROUP BY YEAR(op_date), MONTH(op_date)

⚠️ NOT EXISTS Cataract_Operationdata가 중요함. 백내장 수술 이력이 있는 고객은 기간과 무관하게 통째로 빠짐. 백내장 수술을 받은 분이 나중에 시력교정 수술을 받아도 안 잡힘. 백내장/시력교정 중복 집계를 막으려는 장치지만, 부작용이 있다는 점을 알고 있어야 함.

✅ T-Clareon Vivity 는 EDOF(프리미엄)다 — 2026-08-05 확정. 이름에 Clareon(다초점)과 Vivity(EDOF)가 둘 다 들어 있어 CASE 순서에 따라 갈리는데, EDOF 를 먼저 보는 현재 순서가 맞음. 의학적으로 Vivity 는 EDOF 이고, 레거시 월간보고가 Clareon 계열을 통째로 다초점으로 묶은 쪽이 어긋난 것임. 레거시 PDF 에 맞추려고 CASE 순서를 뒤집지 말 것 (2026-06 다초점 36 vs PDF 33, 2026-07 프리미엄 22 vs PDF 21 — 이 차이는 정상임).

쿼리 (핵심만)

SELECT YEAR(op_date) AS yr, MONTH(op_date) AS mo,
       COUNT(DISTINCT CASE WHEN cat_type='catMulti' THEN eye_key END) AS catMulti,
       COUNT(DISTINCT CASE WHEN cat_type='catMono'  THEN eye_key END) AS catMono,
       COUNT(DISTINCT CASE WHEN cat_type='catEdof'  THEN eye_key END) AS catEdof,
       COUNT(DISTINCT eye_key) AS cataractPatients
FROM (
    SELECT c.OPERATIONR_DATE AS op_date,
           LTRIM(RTRIM(c.CUST_NUM)) + '|' + c.OPERATIONR_DATE + '|R' AS eye_key,   -- ★ 눈 키
           <분류 CASE> AS cat_type
    FROM Cataract_Operationdata c WITH(NOLOCK)
    WHERE c.OPERATIONR_DATE >= :from AND c.OPERATIONR_DATE <= :to
      AND c.OPERATIONR IS NOT NULL AND RTRIM(c.OPERATIONR) <> ''
      AND c.OPERATIONR NOT IN ('X','OP불가','TEST-TEST')
      AND NOT (테스트 고객)
    UNION ALL
    <OPERATIONL / OPERATIONL_DATE 로 같은 블록 반복, eye_key 는 '|L'>
) e
GROUP BY YEAR(op_date), MONTH(op_date)

4. 알아둬야 할 함정

① 유형별 합계 ≠ 전체 인원 (단, PIOL 은 예외)

양쪽 눈에 다른 수술을 할 수 있음. 오른눈 스마일 · 왼눈 라섹이면 smile에도 lasek에도 1명씩 잡히지만 전체 인원(visionPatients)은 1명임. 유형별 숫자를 더해서 전체와 맞추려 하면 안 됨.

예외 — PIOL 5종. 2026-08-05부터 대표유형(우안 우선) 하나에만 집계하므로 icl+tIcl+kpl+tKpl+viva = piolPatients 가 성립함(위 §PIOL 대표유형 참조). 반대로 PIOL 유형별 값은 "그 렌즈를 받은 사람 수"가 아님 — 양안에 다른 렌즈를 넣으면 우안 쪽에만 잡히므로 실제 시술 건수보다 작음(2026-07 ICL: 실제 44명 시술 / 대표유형 41명).

② 시력교정에서 백내장 고객이 통째로 빠짐

NOT EXISTS Cataract_Operationdata가 기간 제한 없이 걸려 있음. 2020년에 백내장 수술을 받은 분이 2026년에 시력교정 수술을 받아도 시력교정수술에 안 잡힘.

③ 수술명 문자열 매칭이라 신규 수술명에 취약함

세 갈래 모두 수술명 텍스트를 LIKE로 훑어 분류함. 새 수술명·새 렌즈명이 도입되면 조용히 other(시력교정)나 단초점(백내장)으로 흘러감. 신규 수술 도입 시 분류 목록 갱신이 필요함.

④ 재수술 판정 — ✅ 2026-07-31 REASON_CD 기반으로 전환 완료

아래 서술은 전환 전 기록임. 2026-07-31 에 01·07·10 제외 + 시술명 Irrigation 보정 규칙으로 SQL 3개 파일에 반영됐음. 전환 후 2026 월별 실측: 01=32 · 02=33 · 03=18 · 04=19 · 05=23 · 06=17 · 07=31. 비교연도도 함께 바뀌었음(2024 213→205 · 2025 279→272). 렌즈/레이저 분류도 행 단위 판정으로 바뀌어 2026 렌즈 103→105. ⚠️ 마트를 읽는 화면이라 SURGERY 도메인 재적재를 해야 반영됨. 상세·승인 범위: 재수술-분류_2026-01~07.md §적용 기록.

단, 사유코드에도 오입력이 있어 시술명 보정을 함께 씀 — 순수 REASON_CD 단독 판정이 아님.

전환 전 기록 (2026-07-29 조사 시점)

RE_OPERATION에는 정규화된 사유 컬럼 REASON_CD(char(3)) / REOP_REASON 이 있고, 2025-01 이후 934건에 12종이 빠짐없이 채워져 있음.

01 Irrigation · 02 ENHANCE · 03 Re-enclavation · 04 Bioptics · 06 Lens Removal · 07 Lens Reposition · 08 Lens Exchange · 09 Keraring · 10 CATARACT · 12 RAINDROP Removal · 13 Ingrowth Removal · 16 enclavation

제외 3종(01·07·10) / 나머지 포함으로 두면 기획 의도와 정확히 맞음.

그런데 현재 쿼리는 이 컬럼을 안 쓰고 시술명 문자열로만 판정함. 2026-01~07 306건 중 8건(2.6%)이 어긋남 — 잘못 제외 4건, 잘못 포함 4건. 4건씩이라 월 합계는 우연히 상쇄되지만 개별 명단은 틀림. 총량만 보면 안 잡히는 종류의 오류임.

재수술 집계·명단 작업 시 문자열 패턴을 늘리지 말고 REASON_CD 기반 전환을 먼저 검토할 것. 단, 재수술 분류 기준은 팀장 검증 대기 상태이므로 기준 변경은 확인 후 착수함.

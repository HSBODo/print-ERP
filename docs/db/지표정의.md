## 1. 검사건수

검사는 **시력교정 · 백내장 · 드림렌즈** 3종으로 구분한다. **각 카테고리는 소스·집계단위가 서로 다르다.**

### 1.1 개요

| 카테고리 | 소스 테이블 | 분류 조건 | 집계 단위 | 대표 검증값 |
|---|---|---|---|---|
| **시력교정검사** | `EXAM` (검사자 리스트) | `EXAM_DATE` 기준, **드림렌즈 분류 제외 + 순수 외래 제외**(2026-07-30, 측정값 무관) | **행/사람** | 2026-04 = 804 (종전 규칙 809) |
| **백내장검사** | `RESERVATION` (백내장검사 예약 `H`) | 기간 내 `H` 예약 내원 + **검안사 배정된 사람** (§1.4) | **사람** | 2026-06 = 55 · 2026-07 = 54 |
| **드림렌즈검사** | `EXAM` (검사자 리스트) | 같은 검사일 렌즈센터 `D`만 있고 검사 `M`이 없는 행 | **행/사람** | 2026-04 = 17 |

> ✅ **2026-07-23 이후 세 카테고리 모두 집계 단위가 "사람"으로 통일**됐다. 백내장의 종전 **눈(좌/우)** 기준은 폐기.
> 종전 눈 기준 검증값(2026-01~04 = 96/66/64/58)은 다른 원장을 본 값이라 더 이상 쓰지 않는다.

### 1.2 공통 규칙

**검사결과 테이블 기반** (시력교정=`EXAM`)
- 날짜 기준: `EXAM_DATE` (char(10), `YYYY-MM-DD`) — 실제 검사일
- **시력교정은 측정값 무관** — 병원 검사자 리스트 행수 기준이라 측정값 미입력 검사도 포함.
- **순수 외래 유입 제외 (2026-07-30 확정)** — 그날 검사(`M`) 내원도, 수술 연계(검사일 이후 수술예약/수술기록,
  재수술 포함)도 없는 EXAM 행은 검사자가 아니다(외래·백내장 예약으로 와서 EXAM 행만 생긴 건).
  판정 배경·월별 영향: [점검/시력교정-검사자_2026-06~07.md](../점검/시력교정-검사자_2026-06~07.md)
- 더 엄격한 "완료" 기준이 필요하면 `STOP_YN='Y'`(중단)·`CANCEL_CD`(취소)를 추가 제외.

**예약 테이블 기반** (백내장)
- 소스: `RESERVATION` 백내장검사 예약(`RESERVE_FLAG='H'`), 날짜 기준 `RESERVE_DATE`
- 검사결과 테이블(`Cataract_Exam`)은 **집계 소스가 아니다** — 상세 컬럼(적절IOL·견적가·검사메모) 조회용 LEFT 성격이다.
- 상세 규칙은 §1.4 참조.

> ⚠️ **폐기된 기준** — "백내장은 추천 수술방법 존재(`OPERATIONR`/`OPERATIONL`)로 **유효 눈** 판정"은
> 2026-07-23 정의 교체로 폐기됐다. 레거시 원장과 다른 화면을 보고 있었다(5월 67 vs 골든 84).

**EXAM + RESERVATION 분류 기반** (드림렌즈)
- 소스: `EXAM WITH(NOLOCK)` 기준 행을 `RESERVATION` 렌즈센터 `D` 예약으로 분류
- 상태: `RESERVE_STATE IN ('I','H')` — 예약(Y)·취소(C) 제외. 이 병원은 'I'에서 멈추므로 사실상 **"내원(체크인)"**.
- 날짜 기준: `RESERVE_DATE`
- 정기검진(FU)은 제외.

### 1.3 시력교정검사

**정의**: 해당 기간에 시력교정 검사를 실제 받은 **사람 수**. 소스는 검사결과 테이블 `EXAM` (병원 "검사자 리스트(상담사별)" 화면과 동일 소스). **EXAM에 섞인 드림렌즈는 제외.**

| 항목 | 값 |
|------|-----|
| 소스 | **`EXAM`** (시력교정 검사결과, PK=`CUST_NUM`) |
| 날짜 기준 | `EXAM_DATE` (char(10), `YYYY-MM-DD`) |
| 측정값 필터 | **없음** — 병원 검사자 리스트 행수 기준(측정값 미입력 검사도 포함). 엄격 "실시"분만 필요하면 `RIGHT01`/`LEFT01` 존재 추가 |
| 드림렌즈 제외 | 같은 날 렌즈센터(`RESERVE_FLAG='D'`) 예약만 있고 시력교정(`'M'`) 예약 없는 EXAM 배제 |
| 순수 외래 제외 | 그날 검사(`M`) 내원 없고 **수술 연계**(수술예약 `RESERVE_DATE`≥검사일·취소 제외 / 수술기록 `OPERATION_DATE`≥검사일) 없는 행 배제 (2026-07-30 확정) |
| 집계 단위 | **사람** = `COUNT(DISTINCT CUST_NUM)` (EXAM은 고객당 1행이라 행수와 동일) |

> **소스가 RESERVATION이 아니라 `EXAM`인 이유**: 병원 공식 "검사자 리스트(상담사별)" 화면(`FrmCounselExamList`)이 시력교정을 `EXAM`+`EXAM_DATE`로 집계한다. "실제 검사 실시" 기준이며 백내장(`Cataract_Exam`)과 동일 구조다. RESERVATION(flag M) 예약기반 집계는 검사 실시와 불일치(과거 정의 843/805 → 본 정의로 교체).
> **드림렌즈 혼입 주의**: `EXAM`에는 검사종류 구분 컬럼이 없어 드림렌즈(CRT/각막굴절교정) 검사가 섞여 있다. 같은 날 렌즈센터(`D`) 예약 기준으로 배제한다.

```sql
SELECT SUBSTRING(e.EXAM_DATE,1,7) AS ym,
       COUNT(DISTINCT e.CUST_NUM) AS visionCorrection
FROM EXAM e WITH(NOLOCK)
WHERE e.EXAM_DATE >= :from AND e.EXAM_DATE <= :to
  AND NOT (                                    -- 드림렌즈 배제
        EXISTS (SELECT 1 FROM RESERVATION rd WITH(NOLOCK)
                WHERE rd.CUST_NUM = e.CUST_NUM AND rd.RESERVE_DATE = e.EXAM_DATE
                  AND rd.RESERVE_STATE IN ('I','H') AND rd.RESERVE_FLAG = 'D')
    AND NOT EXISTS (SELECT 1 FROM RESERVATION rm WITH(NOLOCK)
                WHERE rm.CUST_NUM = e.CUST_NUM AND rm.RESERVE_DATE = e.EXAM_DATE
                  AND rm.RESERVE_STATE IN ('I','H') AND rm.RESERVE_FLAG = 'M')
  )
  AND (                                        -- 순수 외래 제외 (2026-07-30)
        EXISTS (SELECT 1 FROM RESERVATION rm3 WITH(NOLOCK)
                WHERE rm3.CUST_NUM = e.CUST_NUM AND rm3.RESERVE_DATE = e.EXAM_DATE
                  AND rm3.RESERVE_STATE IN ('I','H') AND rm3.RESERVE_FLAG = 'M')
     OR EXISTS (SELECT 1 FROM RESERVATION ro WITH(NOLOCK)
                WHERE ro.CUST_NUM = e.CUST_NUM AND ro.RESERVE_FLAG = 'O'
                  AND ro.RESERVE_STATE <> 'C' AND ro.RESERVE_DATE >= e.EXAM_DATE)
     OR EXISTS (SELECT 1 FROM OPERATIONDATA od WITH(NOLOCK)
                WHERE od.CUST_NUM = e.CUST_NUM AND ISNULL(od.OPERATION_DATE,'') <> ''
                  AND od.OPERATION_DATE >= e.EXAM_DATE)
  )
GROUP BY SUBSTRING(e.EXAM_DATE,1,7)
ORDER BY ym
```

- 보조(엄격 "실시" 기준): 위 조건 + 측정값 존재(`RIGHT01`/`LEFT01`) → 측정 완료분만 02=1585 / 03=850 / 04=799 (데스크는 미입력도 세므로 기본 정의는 측정값 무관).
- **검증 (병원 수기 대조, 종전 규칙)**: 02=1600(병원 1604) / 03=854(853) / 04=809(807) / 05=900. 04월은 병원 엑셀 826행 = EXAM 4월 전체와 1:1 대조로 확정. 드림렌즈 미제외 시 02=1611/03=873/04=826.
- **2026-07-30 순수 외래 제외 반영 (새 규칙 실측)**: 01=1,864 / 02=1,595 / 03=849 / 04=804 / 05=897 / 06=947 / 07(~07-30)=1,044.
  레거시 화면(FrmCounselExamList)은 순수 외래 유입을 계속 포함하므로 새 규칙과 **월 2~5명** 차이가 난다 — 수기 대조 시 참고.
  판정 배경·제외 명단: [점검/시력교정-검사자_2026-06~07.md](../점검/시력교정-검사자_2026-06~07.md)

### 1.4 백내장검사

**정의**: 해당 기간에 백내장검사 예약으로 내원한 고객 중 **검안사가 배정된 사람**을 집계. **사람 단위.**

> **2026-07-23 정의 교체 — 눈(안) → 사람.**
> 레거시 원장인 `BCRM > 통계(C) > 통계_백내장_내원동기`의 원본 SQL을 확보해 재현에 성공했다(6월 55/55 정확 일치).
> 종전 `Cataract_Exam` 추천 IOL **눈** 기준은 **다른 원장**이었다 — 5월 67 vs 골든 84로 −17이 났고, 6월 56 vs 55는 단위가 우연히 근접한 것뿐이다.
> 골든 = 레거시 분류 `백내장` + `중단`. (`F/U`는 외래 추적이라 제외)

| 항목 | 값 |
|------|-----|
| 소스 | **`RESERVATION`**(FLAG='H') + **`CUSTOM`** 담당자 |
| 날짜 기준 | `RESERVE_DATE` (char(10), `YYYY-MM-DD`) |
| 모집단 | `RESERVE_FLAG='H'` · `RESERVE_JINRYO<>'3'`(C_재검사 제외) · `RESERVE_SEQ<>3`(노안5진료실 제외) · `RESERVE_STATE NOT IN ('C','Y')` · `CUST_NUM<>'9999999999999'` · 테스트 고객명 제외 → `DISTINCT CUST_NUM` |
| 포함 조건 | **검안사(`MY_OPTOMETRIST`)가 `EMPLOYEE`에 매칭되는 사람** |
| └ 상담사 = `BS0808`(BS미지정) | 레거시 분류 **중단** → 포함 |
| └ 상담사가 `EMPLOYEE`에 매칭 | 레거시 분류 **백내장** → 포함 |
| └ 검안사 없음 | 레거시 분류 **F/U** → 제외 |
| 집계 단위 | **사람** |

> ⚠️ **`EXISTS(EMPLOYEE)`로 판정할 것.** 레거시 원본의 `(SELECT EMP_NAME ...) = (SELECT EMP_NAME ...)` 패턴은 사실상 IS NOT NULL 검사다.
> `MY_OPTOMETRIST IS NOT NULL`로 옮기면 빈 문자열이 걸려 분류가 뒤집힌다(중단 65 / F/U 3).

```sql
SELECT SUBSTRING(CH.ym,1,7) AS ym, COUNT(*) AS cataract
FROM (
    SELECT DISTINCT B.CUST_NUM, SUBSTRING(D.RESERVE_DATE,1,7) AS ym
    FROM CUSTOM B WITH(NOLOCK)
    JOIN RESERVATION D WITH(NOLOCK) ON D.CUST_NUM = B.CUST_NUM
    WHERE D.RESERVE_DATE >= :from AND D.RESERVE_DATE <= :to
      AND D.RESERVE_FLAG = 'H'
      AND ISNULL(D.RESERVE_JINRYO,'') <> '3'
      AND ISNULL(D.RESERVE_SEQ,0) <> 3
      AND D.RESERVE_STATE NOT IN ('C','Y')
      AND B.CUST_NUM <> '9999999999999'
      AND NOT (ISNULL(B.CUST_NAME,'') LIKE N'%테스트%' OR LOWER(ISNULL(B.CUST_NAME,'')) LIKE '%test%')
) CH
JOIN CUSTOM B WITH(NOLOCK) ON B.CUST_NUM = CH.CUST_NUM
WHERE EXISTS (SELECT 1 FROM EMPLOYEE E WITH(NOLOCK) WHERE E.EMP_NUM = B.MY_OPTOMETRIST)
  AND ( B.MY_COUNSELOR = 'BS0808'
     OR EXISTS (SELECT 1 FROM EMPLOYEE E WITH(NOLOCK) WHERE E.EMP_NUM = B.MY_COUNSELOR) )
GROUP BY SUBSTRING(CH.ym,1,7)
ORDER BY ym
```

  - 종전에는 "레포트=예약 / 리스트=검사기록으로 목적이 달라 의도된 차이(6월 115 vs 114)"라고 기술했으나 **교체로 해소됐다.**
- ⚠️ **레거시 명단의 `검사일자`는 역대 최초 백내장 예약일이다** — 조회 기간과 무관하다. 그래서 **명단을 검사일자 기준으로 훑으면 재방문자가 통째로 빠진다.** 2026-06은 55명 중 신환 43 / 재방문 12, 2026-07은 54명 중 신환 46 / 재방문 8. "명단 세어보니 43명인데 왜 55인가"는 여기서 생기는 착시이며 **55가 맞다.**
- ⚠️ **`Cataract_Exam` 건수를 대조에 쓰지 말 것** — 집계 소스가 아니다. 2026-07은 검사기록 88건인데 레거시 명단도 88행이라 숫자가 같아 보이지만 **겹치는 사람은 81명뿐**이다.
- ⚠️ **`Cataract_Exam`은 `SEQ`로 누적된다** — `EXAM`처럼 고객당 1행 덮어쓰기가 **아니다**. 2026-06 114건 중 13건이 2회차 이상이고 최대 `SEQ`는 3이다. (예: 3936 박연옥 SEQ1 2025-05-02 / SEQ2 2026-06-01)

### 1.4.1 백내장예약률

**정의**: 백내장 추천 눈(안) 중, 백내장 수술예약으로 전환된 비율.

> ⚠️ **분모는 §1.4 백내장검사와 다르다.** §1.4는 2026-07-23 사람 기준으로 교체됐지만, 예약률 분모는
> 레거시 월간보고(~60%대)와 맞추기 위해 **종전 눈(안) 기준(`Cataract_Exam.OPERATIONR/L`)을 유지**한다.
> 2024·2025 하드코딩값(`CATARACT_RATE_LEGACY`)도 눈분모 기준이라 3개년 비교가 정합한다.
> 사람 분모로 통일할지는 별도 결정 사항.

| 항목 | 값 |
|------|-----|
| 화면명 | `백내장예약률 (수술예약건/검사자)` |
| 분모 | 추천 눈 수 (`Cataract_Exam.OPERATIONR/L`) — §1.4와 별개 정의 |
| 분자 | 분모에 포함된 고객 중 취소 아님인 수술예약 `RESERVATION.RESERVE_FLAG='O'` 존재 |
| 날짜 기준 | 분모는 `Cataract_Exam.EXAM_DATE`, 수술예약은 검사자 리스트의 `수술예약등록일` 존재 여부와 동일하게 판정 |
| 집계 단위 | 분모는 **눈(안)**, 분자는 **고객/예약 건** |
| 2024~2025 | 레거시 예약률 표 숫자 고정 사용 |
| 2026 이후 | DB 계산값 사용 |

> **검사 예약등록일은 분자 아님.** 백내장 검사건수 분모는 이미 같은 날 백내장 검사예약(`H`) 내원을 보조조건으로 요구하므로, 검사예약 존재 여부를 분자로 쓰면 사실상 100%가 된다. 예약률 분자는 반드시 **수술예약(`O`)** 이어야 한다.
> `RESERVATION`에는 좌/우 눈 구분이 없으므로 분자는 눈 단위로 증폭하지 않고, 검사자 리스트의 `수술예약등록일` 존재 여부처럼 고객/예약 건 단위로 집계한다.

### 1.5 드림렌즈검사

**정의**: 해당 기간 드림렌즈/렌즈센터 검사 건수. 검사자 리스트와 같은 `EXAM` 기준에서 같은 날 렌즈센터 `D` 예약만 있고 검사 `M` 예약이 없는 행을 집계.

| 항목 | 값 |
|------|-----|
| 소스 | `EXAM` + `RESERVATION` 분류 |
| 진료유형 | `RESERVE_FLAG = 'D'` |
| 상태 | `RESERVE_STATE IN ('I','H')` |
| 세부유형 | 제한 없음 |
| 집계 단위 | **`COUNT(DISTINCT CUST_NUM)` (사람단위)** — 시력교정과 통일 |

> 2026-02만 보고 D/L 계열(`1`,`5`,`7`)로 좁히면 01·03·04월 시력교정 숫자가 더 흔들림. 현재는 원복하여 렌즈센터 `D` 전체를 드림렌즈 분류로 사용.

```sql
SELECT SUBSTRING(e.EXAM_DATE,1,7) AS ym,
       COUNT(*) AS dreamlensPersons
FROM EXAM e WITH(NOLOCK)
WHERE e.EXAM_DATE >= :from AND e.EXAM_DATE <= :to
  AND EXISTS (SELECT 1
              FROM RESERVATION rd WITH(NOLOCK)
              WHERE rd.CUST_NUM = e.CUST_NUM
                AND rd.RESERVE_DATE = e.EXAM_DATE
                AND rd.RESERVE_STATE IN ('I','H')
                AND rd.RESERVE_FLAG = 'D')
  AND NOT EXISTS (SELECT 1
                  FROM RESERVATION rm WITH(NOLOCK)
                  WHERE rm.CUST_NUM = e.CUST_NUM
                    AND rm.RESERVE_DATE = e.EXAM_DATE
                    AND rm.RESERVE_STATE IN ('I','H')
                    AND rm.RESERVE_FLAG = 'M')
GROUP BY SUBSTRING(e.EXAM_DATE,1,7)
ORDER BY ym
```

- **검증**: 02=11 / 03=19 / 04=17 / 05=23 명. 검사자 리스트 전체에서 분리한 값.

### 1.6 함정 (Gotchas)

- **카테고리별 소스·단위 상이**: 시력교정=`EXAM`/사람, 백내장=`RESERVATION`(FLAG='H')+`CUSTOM` 담당자/**사람**(2026-07-23 눈→사람 교체, §1.4), 드림렌즈=`EXAM`+`RESERVATION` 분류/사람. 코드·차트에 소스/단위 라벨 명시 필수.
- **시력교정 소스 주의**: 예약(`RESERVATION` flag M)이 아니라 **검사결과(`EXAM`)** 기준. 예약기반은 병원 공식 수치와 어긋난다.
- **EXAM에 드림렌즈 혼입**: `EXAM`엔 검사종류 구분 컬럼이 없어 드림렌즈(CRT/각막굴절교정) 검사가 월 ~2%(11-21명) 섞인다. 같은 날 렌즈센터(`D`) 예약 기준으로 반드시 배제(미배제 873/826 → 배제 854/809).
- **측정값 필터는 시력교정 기본 정의에서 미적용**: 병원 데스크가 측정값 미입력 검사도 리스트에 세므로 행수 기준으로 맞춘다. 측정값 존재(`RIGHT01`/`LEFT01`) 조건은 엄격 "실시" 보조지표로만(측정분 1585/850/799). 백내장은 측정값이 아니라 추천 수술방법(`OPERATIONR/L`) 기준.
- **EXAM은 스냅샷(고객당 1행) → 과거 월 수치가 사후 감소**: 고객이 나중에 재검사하면 `EXAM_DATE`가 덮어써져 원래 달에서 빠진다. 실측 월 -3~-5명(~0.3%) 수준. 과거 월 수치는 조회 시점에 따라 미세하게 달라질 수 있음.
- **측정값 미입력 검사(월 ~12명)**: `EXAM_DATE`는 해당월인데 `RIGHT01`/`LEFT01`이 빈 검사. 병원 데스크와 본 정의(측정값 무관)는 포함, 엄격 "실시" 보조지표에선 제외.
- **백내장 단위 혼동 금지**: §1.4 백내장검사는 **사람**, §1.4.1 백내장예약률 분모는 여전히 **추천 눈(안)** 이다. 두 지표를 같은 단위로 착각하지 말 것.
- **`Cataract_Exam`은 SEQ 누적** (`EXAM`과 다름): 고객당 1행 덮어쓰기가 아니라 검사할 때마다 `SEQ`가 쌓인다. 2026-06 114건 중 13건이 2회차 이상, 최대 SEQ 3. 따라서 `EXAM`류의 "과거월 소급 감소" 드리프트는 `Cataract_Exam`에 해당하지 않는다. 백내장 검사수의 과거월 변동은 **담당자 재배정**(`CUSTOM.MY_OPTOMETRIST`/`MY_COUNSELOR`)이 원인이다.
- **드림렌즈 분류 기준 주의**: 02월만 보면 D/L 계열만 분리하는 기준이 맞아 보이나, 01·03·04월은 렌즈센터 `D` 전체 분리가 레거시 시력교정 수치에 더 가깝다.
- **드림렌즈 상태값 `I` 단독**: `RESERVATION` `IN('I','H')`는 사실상 "내원(체크인)"이며, 최종 집계는 `EXAM` 행 존재를 함께 요구한다.
- **병원 수기집계와 ±오차 정상**: 병원 자체 수치(시력교정 03=853/04=807 등)는 수기/엑셀 집계라 시스템 정의와 1~2% 차이는 자연스럽다.

#### 1.9.1.1 검사수 안정화 검토 (EXAM 스냅샷 드리프트 — ExamCount 기각)

**문제**: `EXAM`은 고객당 1행(PK=`CUST_NUM`)인 **스냅샷**이라, 5월 검사자가 나중에(6월 등) 재검사하면 `EXAM_DATE`가 새 날짜로 덮여 **과거 월 검사수가 사후 감소**한다(드리프트, 월 −2~−11). 레거시 차트값(1062 등)도 결국 그 시점의 EXAM 스냅샷을 얼린 값이다.

**대안 검토 — 누적/이벤트성 소스로 재정의 시도 (2026-06 prod 전수 점검)**

| 테이블 | 상태 | 판정 |
|---|---|---|
| `EXAM` | 스냅샷(고객당 1행, 덮어씀), 현재 | 공식 소스. 드리프트 존재 |
| `ExamCount` | **append 로그**(고객당 다중, ~48만행), 2026-06까지 라이브 | 유일한 누적이나 아래 사유로 부적합 |
| `EXAM_FU` | 정기검진(follow-up) | 검사수 정의에서 제외 |
| `InspcLst_Exam` / `exam_dto` | 0행(미사용/빈 staging) | ✗ |
| `CHART_EXAM` | 2009~2010만 | ✗ |
| `명동_검사정보_일반` | ~2017 옛 export | ✗ |

**`ExamCount` 기각 사유** (3가지 환산 모두 레거시 초과):

| 환산 방식 | 01 | 02 | 03 | 04 | 05 | 비고 |
|---|--:|--:|--:|--:|--:|---|
| EXAM기준(현재) − 레거시 | 0 | −9 | −6 | +4 | −8 | 총 |오차| 27 |
| ExamCount 단순합집합 − 레거시 | +58 | +55 | +13 | +21 | +10 | 복수검사일·저장중복 과대 |
| ExamCount 고객dedup(2→1) − 레거시 | +58 | +55 | +13 | +21 | +10 | 동일(고객단위 union) |
| ExamCount **정밀 드리프트만** − 레거시 | +11 | −5 | −4 | +6 | −6 | 총 |오차| 32 (악화) |

- `ExamCount`는 **저장 이벤트마다 1행**(5월 raw 3,985 = 검사자 922 × 다중 저장)이고 **재검사·추가검사까지 포함**(넓음). 반대로 EXAM 일부는 누락(5월 distinct 911 < EXAM 922)이라 깔끔한 상위집합도 아님.
- **결정적 반례**: 01월은 드리프트 0(EXAM=레거시=2038)인데 ExamCount 복원은 +11~58을 더한다. 즉 **레거시 숫자 자체가 시점 스냅샷**이라, "완전 복원값"과는 정의가 달라 양쪽을 동시에 만족하는 값이 없다.
- **예약(RESERVATION) 기반**도 검토: 안정적이나 내원/예약 ≠ 검사 실시이며 과대(5월 M-내원 1,103 vs EXAM 922) → 과거 폐기 이력과 동일(§1.3).

**결론 / 방침**

- **검사수 공식 소스 = `EXAM`(+`Cataract_Exam`) 유지.** ExamCount로의 재정의는 정의 불일치로 기각.
- 드리프트 제거는 **월마감 freeze**(§3 일별 산출물 저장)로 한다 — 레거시가 한 것과 동일하게, 월이 닫히면 그 시점 검사수를 확정 저장. 이것이 유일하게 자기일관적이다.
- `ExamCount`는 측정값·추세 분석용 **보조 로그**로만 활용한다(카운트 소스 아님).

#### 1.9.2 원데이 검사

**정의**: 레거시 "원데이 검사" 차트를 재현하기 위한 검사OP 기반 검사 건수. 실제 같은 날 수술 여부가 아니라, 검사자 리스트(`EXAM`) 중 같은 날 `RESERVATION` 시력교정 검사예약 `M/5(검사OP)`로 내원한 건을 센다.

| 항목 | 값 |
|---|---|
| 소스 | `EXAM` + `RESERVATION` |
| 날짜 기준 | `EXAM.EXAM_DATE` |
| 원데이 판정 | 같은 고객·같은 날짜 `RESERVATION.RESERVE_FLAG='M'`, `RESERVE_JINRYO='5'`, `RESERVE_STATE IN ('I','H')` 존재 |
| 제외 | 테스트 고객명/검사메모/예약번호만. ⚠️ **중단/취소(`STOP_YN`·`CANCEL_CD`) 제외는 2026-07-30 폐기** — 수술 가능 여부는 검사 결과이지 검사 종류가 아니다 ([점검/원데이-레거시-비교](../점검/원데이-레거시-비교_2026-07.md) §5) |
| 집계 단위 | `COUNT(*)` (EXAM 행/사람 단위) |

```sql
SELECT SUBSTRING(e.EXAM_DATE,1,7) AS ym,
       COUNT(*) AS oneDayExamCount
FROM EXAM e WITH(NOLOCK)
JOIN CUSTOM cu WITH(NOLOCK) ON cu.CUST_NUM = e.CUST_NUM
WHERE e.EXAM_DATE >= :from AND e.EXAM_DATE <= :to
  -- 2026-07-30: 중단/취소(STOP_YN·CANCEL_CD) 단서 제거 — 원데이 = 당일OP 예약 기준
  AND NOT (
    ISNULL(cu.CUST_NAME, '') LIKE N'%테스트%'
    OR LOWER(ISNULL(cu.CUST_NAME, '')) LIKE '%test%'
    OR ISNULL(e.EXAM_MEMO, '') LIKE N'%테스트%'
    OR LOWER(ISNULL(e.EXAM_MEMO, '')) LIKE '%test%'
  )
  AND EXISTS (
    SELECT 1
    FROM RESERVATION r WITH(NOLOCK)
    WHERE r.CUST_NUM = e.CUST_NUM
      AND r.RESERVE_DATE = e.EXAM_DATE
      AND r.RESERVE_FLAG = 'M'
      AND r.RESERVE_STATE IN ('I','H')
      AND r.RESERVE_JINRYO = '5'
      AND LOWER(ISNULL(r.RESERVE_NUM, '')) NOT LIKE '%test%'
      AND LOWER(ISNULL(r.RESERVE_NUM, '')) NOT LIKE '%kiosktest%'
  )
GROUP BY SUBSTRING(e.EXAM_DATE,1,7)
ORDER BY ym
```

### 1.10 검사자 직업 구성 (직장인 / 학생 / 기타)

**정의**: `검사수`(§1.9.1) 모집단을 검사자 본인의 **직업**으로 3분류한 구성비 지표. 레거시 "총검사자" 표의 `직장인/학생/기타` 칼럼을 재현한다.

| 항목 | 값 |
|------|-----|
| 모집단 | **검사수와 동일** = `EXAM` 행 + `Cataract_Exam` 행 (행 단위, §1.9.1). 3버킷 합 = 검사수 |
| 소스 | **`CUSTOM.JOB`** (검사자 `CUST_NUM`으로 1:1 조인) |
| 분류 단위 | 행(검사 세션). 동일인이 시력교정+백내장 둘 다면 각각 1행으로 직업이 두 번 계수됨(검사수와 동일) |
| 2024~2025 | 레거시 확정값 고정 (DB 재집계 안 함) |
| 2026 이후 | prod DB 계산 |

> **`CUSTOM.JOB`은 코드값이 아니라 자유 입력 텍스트**다(직장인·회사원·사무직·대학생·학생·주부… 수백 종, 공백 다수). 그래서 키워드 매핑 사전으로 3버킷 롤업이 필요하다.

#### 버킷 롤업 규칙

`j = LTRIM(RTRIM(ISNULL(CUSTOM.JOB,'')))` 기준, 위에서부터 우선 적용:

```sql
CASE
  -- ① 직장인 우선 가드: 교사/교수/교직원/강사는 학생 패턴(②)보다 먼저 처리
  --    ("고등학교 교사"가 '%고등%'에 걸려 학생으로 새는 버그 방지)
  WHEN j LIKE N'%교사%' OR j LIKE N'%교수%' OR j LIKE N'%교직원%' OR j LIKE N'%강사%' THEN N'직장인'
  -- ② 학생: 학생/대학원생/수험생/재수생/신입생/초·중·고[숫자]/초·중·고등/대입·대학예정/졸업예정/졸업생
  WHEN j LIKE N'%학생%' OR j LIKE N'%대학원생%' OR j LIKE N'%수험생%'
    OR j LIKE N'%재수생%' OR j LIKE N'%신입생%'
    OR j LIKE N'초[0-9]%' OR j LIKE N'중[0-9]%' OR j LIKE N'고[0-9]%'
    OR j LIKE N'%초등%' OR j LIKE N'%중학%' OR j LIKE N'%고등%' OR j LIKE N'%고3%'
    OR j LIKE N'%대학%예정%' OR j LIKE N'%졸업%예정%' OR j LIKE N'%졸업생%' OR j LIKE N'%대입%'
    OR j = 'university' THEN N'학생'
  -- ③ 군인/대체복무 → 기타 (군인 변형·사회복무요원·공익근무 포함)
  WHEN j LIKE N'%군인%' OR j LIKE N'%사회복무%' OR j LIKE N'%공익근무%' THEN N'기타'
  -- ④ 사무직 → 직장인 (아래 '무직' 부분일치 버그 방지용 선처리)
  WHEN j = N'사무직' THEN N'직장인'
  -- ⑤ 기타: 무직/주부/가사/취업준비/취준/휴식·휴직/퇴직·은퇴/빈값표기(없음·N·None)/공백
  WHEN j IN ('', '.', N'무', N'無', N'무 직', N'무직', N'없음', 'N', 'None', 'none', N'가사', N'주부',
             N'휴식', N'휴식중', N'휴직중', N'취업준비', N'취업준비중', N'취업준비(휴식)', N'취업준비/휴식중',
             N'군입대 직전', N'입대 전', N'기타')
    OR j LIKE N'%주부%' OR j LIKE N'%취업준비%' OR j LIKE N'%취준%'
    OR j LIKE N'%퇴직%' OR j LIKE N'%은퇴%' OR j LIKE N'%휴직%' THEN N'기타'
  -- ⑥ 그 외 전부 → 직장인 (회사원·전문직·자영업/프리랜서 등)
  ELSE N'직장인'
END
```

**핵심 규칙 (레거시 일치의 열쇠)**

| 규칙 | 이유 |
|------|------|
| **군인/대체복무 → 기타** | 레거시가 의무복무·대체복무를 직장인이 아닌 기타로 집계. `%군인%`(군인(진) 등 변형)·사회복무요원·공익근무 포함. (4월 36명이 직장인↔기타 스윙의 주범) |
| **사무직 → 직장인** | `LIKE '%무직%'`이 "사**무직**"을 무직(기타)으로 오분류하던 버그. `=` 선처리로 고정 |
| **교사/교수/교직원/강사 → 직장인 (학생보다 우선)** | "고등학교 교사"가 `%고등%`에 걸려 학생으로 새던 버그. 직장인 가드를 ①에 둬 차단 |
| **재수생·신입생·중[숫자]·고[숫자]·대입·입학/졸업예정·졸업생 → 학생** | 자유입력 경계어. 룰이 직장인으로 보던 학생들 (예: 중2·대입예정자·대입준비). |
| **빈값표기(없음·N·None)·가사 → 기타** | 공백 대신 텍스트로 적힌 "없음/N/None", 가사(주부류)를 기타로. |
| **퇴직·은퇴·휴직·취준 → 기타** | 비근로 상태(퇴직/은퇴/정년퇴직/휴직/취준생)를 직장인에서 분리. |

#### 함정 (Gotchas)

- **`JOB`는 자유텍스트** — 코드 테이블이 없다. 신규 직업 표현이 계속 유입되므로 `ELSE → 직장인` 기본값이 미분류를 흡수한다. 매핑 사전은 주기적 점검 대상.
- **`'%무직%'` 부분일치 주의** — `사무직`이 걸린다. 반드시 `사무직 = 직장인`을 먼저 처리.
- **`'%고등%'` 부분일치 주의** — `고등학교 교사`가 학생으로 걸린다. 교사/교수/교직원/강사 직장인 가드를 학생 패턴보다 **먼저** 둬야 한다.
- **군인 분류는 정책 결정** — 레거시 일치를 위해 기타로 둔다. 회사 기준 변경 시 이 한 줄만 수정.
- **단위는 행(검사수)** — 사람 수가 아니다. 동일인 복수 검사가 각각 계수된다.

## 2. 수술건수

수술은 **실제 수술일자** 기준으로 집계한다. 수술예약일/예약등록일이 아니라 실제 수술 실행 테이블을 기준으로 함.

### 2.1 개요

| 카테고리 | 소스 테이블 | 날짜 기준 | 집계 단위 | 비고 |
|---|---|---|---|---|
| **시력교정수술** | `OPERATIONDATA` | `OPERATION_DATE` | **사람** (`DISTINCT CUST_NUM`) | 백내장 수술 고객 제외 |
| **백내장수술** | `Cataract_Operationdata` | `OPERATIONR_DATE` / `OPERATIONL_DATE` | **눈(안)** (`CUST_NUM + 수술일 + R/L`) | 레거시 백내장 수술건수 기준 |

### 2.2 공통 규칙

- 테스트 고객 제외: 고객명 `테스트`, `test` 포함 제외.
- 무효 수술코드 제외: `X`, `OP불가`, `모든수술가능`, `op x`, `Strabismus`, `TEST-TEST`.
- 시력교정은 `Cataract_Operationdata`에 존재하는 고객을 제외하여 백내장 중복 혼입 방지.
- `전체 수술건수`는 세부 수술명 합산이 아니라 `시력교정수술 인원 + 백내장수술 눈 수`.
- 세부 수술명은 양안에 서로 다른 수술명이 들어갈 수 있어 유형별 합계와 전체 인원이 반드시 같지 않음.

### 2.3 시력교정수술

**정의**: 해당 기간 실제 시력교정 수술을 받은 사람 수. 레거시 "시력교정 검사 후 수술" 표와 대조한 결과, 수술예약보다 `OPERATIONDATA.OPERATION_DATE` 실제 수술 기준에 가장 가까움.

```sql
SELECT SUBSTRING(o.OPERATION_DATE,1,7) AS ym,
       COUNT(DISTINCT o.CUST_NUM) AS visionPatients
FROM OPERATIONDATA o WITH(NOLOCK)
JOIN CUSTOM cu WITH(NOLOCK) ON cu.CUST_NUM = o.CUST_NUM
WHERE o.OPERATION_DATE >= :from AND o.OPERATION_DATE <= :to
  AND NOT EXISTS (
      SELECT 1
      FROM Cataract_Operationdata co WITH(NOLOCK)
      WHERE co.CUST_NUM = o.CUST_NUM
  )
  AND (
       (NULLIF(LTRIM(RTRIM(ISNULL(o.OPERATIONR,''))), '') IS NOT NULL
        AND o.OPERATIONR NOT IN ('X','OP불가','모든수술가능','op x','Strabismus','TEST-TEST'))
    OR (NULLIF(LTRIM(RTRIM(ISNULL(o.OPERATIONL,''))), '') IS NOT NULL
        AND o.OPERATIONL NOT IN ('X','OP불가','모든수술가능','op x','Strabismus','TEST-TEST'))
  )
  AND NOT (
      ISNULL(cu.CUST_NAME, '') LIKE N'%테스트%'
      OR LOWER(ISNULL(cu.CUST_NAME, '')) LIKE '%test%'
  )
GROUP BY SUBSTRING(o.OPERATION_DATE,1,7)
ORDER BY ym
```

### 2.4 백내장수술

**정의**: 해당 기간 실제 백내장 수술 눈 수. 우/좌 수술일을 펼친 뒤 `CUST_NUM + OPERATION_DATE + R/L`을 1건으로 집계. 동일인이 같은 날 양안 수술하면 2안으로 집계.

```sql
SELECT SUBSTRING(x.OPERATION_DATE,1,7) AS ym,
       COUNT(DISTINCT x.CUST_NUM + '|' + x.OPERATION_DATE + '|' + x.eye) AS cataractPatients
FROM (
    SELECT CUST_NUM, OPERATIONR_DATE AS OPERATION_DATE, OPERATIONR AS OPERATION, 'R' AS eye
    FROM Cataract_Operationdata WITH(NOLOCK)
    UNION ALL
    SELECT CUST_NUM, OPERATIONL_DATE AS OPERATION_DATE, OPERATIONL AS OPERATION, 'L' AS eye
    FROM Cataract_Operationdata WITH(NOLOCK)
) x
JOIN CUSTOM cu WITH(NOLOCK) ON cu.CUST_NUM = x.CUST_NUM
WHERE x.OPERATION_DATE >= :from AND x.OPERATION_DATE <= :to
  AND NULLIF(LTRIM(RTRIM(ISNULL(x.OPERATION,''))), '') IS NOT NULL
  AND x.OPERATION NOT IN ('X','OP불가','TEST-TEST')
  AND NOT (
      ISNULL(cu.CUST_NAME, '') LIKE N'%테스트%'
      OR LOWER(ISNULL(cu.CUST_NAME, '')) LIKE '%test%'
  )
GROUP BY SUBSTRING(x.OPERATION_DATE,1,7)
ORDER BY ym
```

## 3. 산출물 저장 전략 — 주간 승인 + 월 마감 스냅샷

> **확정 방침(2026-08-05)**: 드리프트 제거는 **주간 승인 → 월 마감 스냅샷**으로 한다.
> 종전 초안의 *"2026년 이후 전 지표 일별 산출물 저장 후 합산"* 은 **폐기**한다 — 일별 저장은 범위 밖이다.
> (구 `db/지표-마감스냅샷-기획.md` 를 이 절로 흡수하고 그 문서는 삭제했다.)

### 3.1 왜 필요한가

- `EXAM` 은 고객당 1행 스냅샷 → 재검사하면 **과거월 수치가 사후 감소**(§1.9.1.1).
- `RESERVATION` 상태값(`I`/`H`)은 늦은 내원·정정으로 **과거월 행수가 사후 증가**
  (외래수 2026-01 레거시 4,822 vs 현재 4,831).
- 백내장 분류는 `CUSTOM` 의 **현재** 담당자 값을 보므로 재배정 시 지난 달이 바뀐다(§1.4).
- 지금도 2024~2025 는 **시드(=수동 스냅샷)** 로 고정 중이다. 이걸 테이블로 정식화하는 것이 목표다.

### 3.2 핵심 원칙 (한 줄)

> **(지표, 기간) 승인/마감 스냅샷이 있으면 그 값을 쓰고, 없으면 라이브로 계산한다.**

| 상황 | 표시 | 상태값 |
|---|---|---|
| 마감된 과거월 (월 스냅샷 존재) | **확정값** — 다시는 안 변함 | `confirmed` |
| 승인된 과거주 (주간 스냅샷 존재) | **승인값** — 주간 리포트 재현 | `approved` |
| 당월·미마감월·미승인주 | **라이브 계산** (잠정) | `provisional` |

응답 DTO 에 `status` 한 필드만 추가한다.

### 3.3 테이블 (월 확정 1 + 주간 승인 1)

운영 앱 DB(Postgres)에 저장한다. **CRM MSSQL 은 READ-ONLY 라 쓰지 않는다.**

```sql
CREATE TABLE metric_monthly_snapshot (
  metric_key    VARCHAR(40) NOT NULL,   -- exam_count · outpatient_count · vision_exam · cataract_exam …
  year          INT         NOT NULL,
  month         INT         NOT NULL,   -- 1~12
  value         INT,
  rule_version  VARCHAR(20) NOT NULL,   -- 산출 기준 버전
  generated_at  TIMESTAMP   NOT NULL,
  PRIMARY KEY (metric_key, year, month)
);

CREATE TABLE metric_weekly_snapshot (
  metric_key    VARCHAR(40) NOT NULL,
  year          INT         NOT NULL,
  month         INT         NOT NULL,   -- 월 경계 기준
  week_index    INT         NOT NULL,   -- 그 달의 1~6주차
  week_start    DATE        NOT NULL,
  week_end      DATE        NOT NULL,   -- 월 경계를 넘으면 그 달 말일로 클립
  value         INT,
  rule_version  VARCHAR(20) NOT NULL,
  approved_at   TIMESTAMP   NOT NULL,
  approved_by   VARCHAR(80) NOT NULL,
  PRIMARY KEY (metric_key, year, month, week_index)
);
```

단위·소스 등 메타는 코드/문서가 갖고 있으므로 테이블엔 최소한만 둔다.

### 3.4 쓰기(마감) 흐름

운영 순서는 **주간 승인 → 월 마감**이다. 1단계는 관리자 수동 버튼만으로 충분하다.

| 동작 | 엔드포인트(안) | 결과 |
|---|---|---|
| 주간 승인 | `POST /api/admin/metric-snapshot/approve-week?weekStart=&weekEnd=` | 그 주 전 지표 라이브 계산 → 주간 스냅샷 upsert |
| 월 마감 | `POST /api/admin/metric-snapshot/close-month?ym=2026-05` | 승인주 합계 vs 월 라이브 비교 후 월 스냅샷 upsert |
| 재승인·재마감 | 같은 호출 반복 | 덮어쓰기 (데이터 정정·규칙 변경 시) |
| 해제(풀기) | `DELETE /api/admin/metric-snapshot?ym=2026-05` | 스냅샷 삭제 → 다시 라이브(잠정) |

- 수정은 별도 편집 기능 없이 **풀기 → 다시 계산 → 다시 저장**으로 처리한다. 직접 숫자 수정은 안 한다.
- 승인주·확정월을 영구 불변으로 잠그지 않는다 — 현실적으로 정정이 생긴다.
- **이력은 남기지 않는다**(덮어쓰면 이전 값 소실). 필요해지면 별도 감사 테이블로 확장.
- `rule_version` 이 바뀌는 전역 규칙 변경 = 해당 지표 전체 월 일괄 재마감.

화면은 조회 1벌 그대로 두고 **마감관리** 메뉴(스냅샷 현황 · 주간 승인 · 월 마감)만 추가한다.

## 5. 예약 (종합 · 온라인 · 콜)

### 5.1 예약 종합 (콜 · 온라인)

레거시 BCRM "문의통계(RSS)" 화면(`uSTATISTICSD1`)의 검사예약 채널 집계를 재현. **한 화면 3탭**: 예약 종합(콜+온라인) · 온라인 예약(네이버·카카오·홈페이지) · 콜 예약(인콜·아웃콜).

- **2024~2025**: 레거시 차트 확정값 고정.
- **2026년 이후**: 운영 DB 추정치. **등록일(`InsertedDateTime`) 기준** — RSS 화면이 등록일로 집계하기 때문. 예약일(`RESERVE_DATE`)로 세면 타월 예약 혼입으로 차트와 어긋남(특히 2월 +20%).

#### 5.1.1 정의

| 항목 | 값 |
|---|---|
| 화면 | `/stats/reservation-overall` (메뉴: `예약 > 예약 종합`, 3탭) |
| 소스 | `RESERVATION` (`RESERVE_FLAG='M'`, `RESERVE_JINRYO IN ('','5','6','7','24','25')`) |
| 날짜 기준 | **`InsertedDateTime`(등록일)**. 미래 불가 → 당월까지 자연 완결, 이후 월 null |
| **콜** | `RESERVE_PATH IN ('CTI','CRM')` (인콜=CTI·아웃콜=CRM). **B2B(군인)·재검·중복 제외**: `RESERVE_SEQ NOT IN ('8','5')` + `COMMENT NOT LIKE` `%B2B(군인)%`/`%재검%`/`%중복%`/`%시뮬%`/`%차트있음%` |
| **온라인** | `RESERVE_PATH IN ('ONLINE','APP','NAVER')` (홈페이지=ONLINE·APP, 네이버=NAVER). **제외 미적용**(B2B군인이 온라인엔 거의 없어 적용 시 과소) |
| **종합** | 콜 + 온라인 (경로 상호배타 → `union DISTINCT`) |
| 집계 단위 | `COUNT(DISTINCT RESERVE_NUM)` |
| 2024~2025 | 레거시 확정값 고정 (DB 재집계 안 함) |
| 2026 이후 | DB 라이브 (mssql 프로파일) |

```sql
-- callFilter (콜 채널, B2B군인·재검·중복 제외):
--   r.RESERVE_PATH IN ('CTI','CRM')
--   AND ISNULL(r.RESERVE_SEQ,'') NOT IN ('8','5')
--   AND ISNULL(r.COMMENT,'') NOT LIKE '%B2B(군인)%' AND ... NOT LIKE '%재검%'/'%중복%'/'%시뮬%'/'%차트있음%'
SELECT YEAR(r.InsertedDateTime) AS yr, MONTH(r.InsertedDateTime) AS mo,
  COUNT(DISTINCT CASE WHEN (callFilter) OR r.RESERVE_PATH IN ('ONLINE','APP','NAVER')
                      THEN r.RESERVE_NUM END) AS 종합,
  COUNT(DISTINCT CASE WHEN r.RESERVE_PATH IN ('ONLINE','APP','NAVER') THEN r.RESERVE_NUM END) AS 온라인,
  COUNT(DISTINCT CASE WHEN (callFilter) THEN r.RESERVE_NUM END) AS 콜
FROM RESERVATION r WITH(NOLOCK)
WHERE r.InsertedDateTime >= :from AND r.InsertedDateTime <= :to
  AND r.RESERVE_FLAG='M' AND r.RESERVE_JINRYO IN ('','5','6','7','24','25')
  AND NOT (r.CUST_NAME LIKE '%테스트%' OR r.CUST_NAME LIKE '%TEST%' OR r.CUST_NUM='8888888888888')
GROUP BY YEAR(r.InsertedDateTime), MONTH(r.InsertedDateTime)
```

- **RSS 수기 테이블은 폐기됨**: 네이버/카카오 수기 입력 테이블 `[220.85.109.240].MCRM.dbo.OnLineReservation`은 1행(2024-07, 삭제)뿐, 인입콜 캐시 `RSS`도 31행(2025-08~11)뿐. 현재 네이버는 `RESERVE_PATH='NAVER'`로 통합됨.
- **카카오는 `RESERVE_PATH` 없음**: 해피톡 채널이라 RESERVATION에 거의 안 잡힘(`HappyTalk_Counsel_List` ★신환 월 9~16건). 온라인 합산엔 사실상 미포함이나 차트도 비슷.
- **렌삽(JINRYO 24/25)·취소(STATE='C')는 손대지 말 것**: 렌삽은 `FLAG='M'`엔 0건이라 무관, 취소 제외는 과도(−376)라 차트와 멀어짐.
- **B2B(군인) 제외는 콜에만**: `RESERVE_SEQ='8'` 군인 단체예약 월 ~80건이 콜로 유입. 온라인에 같은 제외 적용 시 과소.
- **EICN_MySQL 링크드서버는 우리 연결에서 작동**: 진짜 공식값이 필요하면 `OPENQUERY(EICN_MySQL,...)`로 인입콜까지 재현 가능(별도 계정 불필요).

| 5 | 백내장 | 전체(노안포함) · 만 · 중단제외 · 예약 · 예약률 · 전환률 | 건 / % | §1.4 4분류에 **1:1 대응**(2026-08-05). 전체=리스트 전체 · 만=백내장+중단 · **중단제외=`백내장` 분류만** — 공란 해소 |
| 6 | 중단 | 중단수 · 중단율 | 건 / % | **중단수**=`EXAM.STOP_YN='Y'` 월별. **중단율**=중단수÷검사건수 시력교정(레거시 검산 일치). ⚠️ EXAM 스냅샷이라 과거월 사후 변동 |
| 7 | 검사 건수 | 시력교정 · 드림렌즈 · 백내장 · 노안2 · 합계 | 건 | §1.3/§1.5/§1.4. **노안2 = 백내장 `전체(노안포함) − 만`**(블록5 idx9−idx10). **합계 = 시력교정+드림렌즈+백내장+노안2** |
| 8 | 검사 비율 | 시력교정 · 드림렌즈 · 노안 · 백내장 · 노안2+5대질환 | % | 블록7의 비율. **분모 = `합계`** |
| 9 | 원데이/일반검사 | 시력교정 · 원데이 · 원데이예약 · 일반검사 · 일반검사예약 · 일반검사비율 · 원데이성공률 · 일반성공률 | 건 / % | 원데이 §1.9.2. 원데이예약=원데이 후 7일 이내 유효 시력교정 수술 존재. 일반검사=시력교정−원데이, 일반검사예약=시력교정 수술예약−원데이예약 |

### 6.3 2026 산출 시 주의 (정합성)

- **총검사자**: §1.9.1 검사수 그대로. ✅ 산출 가능
- **직업(직장인/학생/기타)**: §1.10 룰. prod 4개월 검증 레거시 ±1.5%. ✅ 산출 가능
- **검사 건수 시력교정·드림렌즈**: §1.3/1.5. ✅ 운영 DB 라이브 산출. **합계 = 시력교정+드림렌즈+백내장+노안2**.
- **백내장 funnel(전체(노안포함)·만·중단제외·노안2) + 검사건수 '백내장'** — ✅ **2026-08-05 개편으로 §1.4 4분류에 그대로 대응한다.**

  | 종합표 칼럼 | §1.4 분류 대응 | 2026-06 | 2026-07 |
  |---|---|---:|---:|
  | **전체(노안포함)** | 리스트 전체 = 백내장+중단+노안/FU+기타 | 115 | **102** |
  | **만** | `백내장` + `중단` (= 월간 레포트 백내장 검사수) | 55 | **56** |
  | **중단제외** | `백내장` 만 (= 만 − 중단) | 45 | **45** |
  | **노안2** | `노안/FU` + `기타` (= 전체 − 만) | 60 | **46** |
  | 검사건수 블록 '백내장' | **`만` 과 동일값** | 55 | 56 |

  **`전체` 정의가 바뀌었다** — 종전 `Cataract_Exam` 검사기록 세션(2026-07 = 88)에서
  **`RESERVATION`(`H`) 예약 기반 리스트 전체**(102)로 교체됐다. `Cataract_Exam` 은 이제 집계 소스가 아니다.
  종전 정적 입력값(전체 라이브 145/100/128/110/132/64, 엑셀 153/106/135/110)은 **모두 옛 정의**다.

  ✅ **`중단제외` 공란이 해소됐다** — 4분류가 생기면서 `백내장` 분류 자체가 곧 중단제외다.

  ⚠️ 여전히 **과거월이 소급 변동**한다. 원인은 `Cataract_Exam` 스냅샷이 아니라
  **`CUSTOM` 담당자 재배정**(§1.4)이다. 확정은 **월 마감 freeze**로(§3).
  2026-01~05 는 V22/V27 골든 시드가 우선이라 이 개편이 소급 적용되지 않는다 — **2026-06부터** 봐야 한다.

  예약률 = 예약 ÷ 만.
- **중단수·중단율**: 중단수=`EXAM.STOP_YN='Y'`, 중단율=중단수÷시력교정. ✅ 산출 가능
- **검사 비율**: 분모는 검사 건수 `합계`. 2026은 시력교정·드림렌즈·백내장·노안2+5대질환 비율을 반영하고, 별도 `노안` 분류값은 현재 0.0%로 둔다.
- **원데이/일반검사**: ✅ 산출 가능. `원데이`는 §1.9.2. `원데이예약`은 이름과 달리 단순 수술예약(`O`) 존재가 아니라, 레거시 표와 대조 시 **원데이 검사 후 7일 이내 유효 시력교정 수술 존재**가 가장 가깝다. 2026-01~04는 레거시 스냅샷값(804/839/422/381)을 우선 반영했고, 05~06은 같은 기준으로 운영 DB에서 산출했다. `일반검사=시력교정−원데이`, `일반검사예약=시력교정 수술예약−원데이예약`, `일반검사비율=일반검사÷시력교정`, `원데이성공률=원데이예약÷원데이`, `일반성공률=일반검사예약÷일반검사`.

**원데이예약 원인 조사 (2026-01~04)**:

| 기준 | 01 | 02 | 03 | 04 | 판정 |
|---|--:|--:|--:|--:|---|
| 화면/레거시 스냅샷 | 804 | 839 | 422 | 381 | 적용값 |
| 단순 수술예약 O 존재 | 842 | 866 | 440 | 411 | 과대(+18~38) |
| 당일 수술예약/당일 실제수술 | 778 | 808 | 409 | 371 | 과소 |
| 유효 시력교정 수술 7일 이내(현재 DB) | 810 | 839 | 428 | 388 | 최접근. 잔차는 EXAM/OPERATIONDATA 스냅샷·사후 입력 차이로 판단 |
- **소개유형(일반/고객소개/직원소개)**: `MOTIVE_NEW02.category01_name` — **고객소개=`소개고객`+`소개미확인`**, 직원소개=`소개직원`, 일반=잔차. 레거시가 `소개미확인`(소개자정보 0%)을 고객소개로 편입한 것을 2026-06-22 prod 검증으로 확인해 동일 적용 → 레거시 월간보고와 정합(2026 1~4월 평균차 고객소개 ~13건·일반 ~10건, 기존 ~110/~106건에서 수렴). EXAM 덮어쓰기 스냅샷 특성상 과거월은 소폭 소급변동 가능.
- ~~**남은 공란**: 백내장 `중단제외`~~ → ✅ **해소** (2026-08-05, 위 funnel 표 참조). 2026-06 이후 공란 없음.

**함정**:
- **`합계` ≠ 총검사자 — 2024~2025 한정.** 검사 건수 블록이 별도 집계라 어긋났다(예: 2024-04 합계 1,167 vs 총검사자 1,140).
  **2026-06 이후로는 일치한다** — 개편으로 검사수의 백내장 몫이 리스트 전체(102)가 되면서
  `시력교정 + 드림렌즈 + 만 + 노안2 = 총검사자` 가 성립한다.
  검산(2026-07): `1,074 + 28 + 56 + 46 = 1,204` = 검사수(§1.9.1) ✓
- **검사 비율 5칼럼 ≠ 검사 건수 4칼럼** — 비율 블록은 `노안`을 별도로 두어 분류가 다르다. 분모는 `합계`.
- **`만`(56)과 검사수의 백내장 몫(102)을 섞지 말 것** — 종합표 안에 두 숫자가 같이 있다.
  월간 레포트·`/stats/cataract-exam-list` 요약 칩의 "백내장검사수"는 **만(56)** 이다.

- ✅ **주간 표는 운영 DB 라이브** — [OverallExamWeeklyPage.tsx](../../frontend/src/pages/exam/OverallExamWeeklyPage.tsx) (`전체지표 > 주간 검사자 종합지표` 메뉴, `/stats/overall-exam-weekly`). 백엔드 `GET /api/stats/overall-exam/weekly?years=` ([OverallExamWeeklyController](../../backend/src/main/java/com/bviit/analytics/overall/controller/OverallExamWeeklyController.java)·Service·Repository). 일자별 집계를 **주(월~일)로 버킷팅**한다.
  - **주 정의**: 월요일~일요일, 월 경계를 걸친 주는 **각 달로 잘라 귀속**. **1일~첫 월요일 직전의 선행 부분 구간은 첫 정규 주에 합쳐 1주로 만든다**(1주 = 1일~첫 일요일, 마지막 주만 부분 주). 검증: 2026-02(1일=일) → 1주 02/01~08·2주 09~15·…·4주 23~28(부분), 2026-05(1일=금) → 1주 05/01~10·…, 모두 주 합계 = 월 검사수 일치(05=1054).
  - **전 구간 DB 라이브**(2024~25 레거시 고정값은 월 단위라 주로 분해 불가). SQL 본문은 §1.3~1.10 월별 쿼리와 동일하고 집계 단위만 일자로 바꿈. 백내장 `전환률`은 월별과 동일하게 공란. **소개유형**은 우리 DB 기준(MOTIVE_NEW02 `소개고객`)이라 레거시와 차이 있을 수 있음(§6.3).
  - ⚠️ **백내장 개편은 주간 표에 이미 반영된다** — 공유 조각(`fragments/exam-session-source.sql`)을 쓰므로
    2026-06 이후 주 합계의 백내장 몫이 리스트 전체(102) 기준으로 바뀐다. 월별 정적 표와 어긋나 보이면
    **월별 쪽이 미갱신**인 것이다(위 §6.4 경고). `중단제외`도 주간에서는 산출 가능해졌다.

## 1. 배경

현재 **B&VIIT 대시보드 배치**는 매일 새벽 SOFTCRM(MSSQL 운영 DB)에 JDBC 로 직접 접속하여 데이터를 읽고, Postgres 마트(집계 저장소)에 적재하는 구조로 운영 중입니다.

이 접근 방식을 **사내 데이터 플랫폼에서 데이터를 공급받는 구조**로 전환하려 합니다. 이 문서는 그 전환 준비를 위해, **현재 배치가 어느 테이블을 어떻게 참조하는지** 를 정리한 것입니다.

---

## 2. 한눈에 보기

```
[MSSQL 운영 DB + 링크드서버]         ← 이관 대상
  └─ 31개 테이블                       총 3그룹으로 분류
      ├─ 예약·검사·수술·기본정보·코드 (19개) → 매일 필수
      ├─ 카카오톡 상담 (4개)           → 매일 필수 (예약통계 화면)
      └─ 예약통계·CTI·네이버·B2B·드림렌즈 (8개) → 매일 필수 (예약통계·B2B·드림렌즈 장부)
         · 그중 2개는 SOFTCRM 이 걸어놓은 링크드서버 원격 테이블
           (EICN_MySQL.stat_user_inbound_bseye · [220.85.109.240].IPLUS.PAOSUNAB)

[MariaDB 홈페이지]                   ← 이번 이관 대상 아님 (참고)
  └─ TBL_COUNSEL (1개)
```

- **이관 대상 테이블 총 31개** (SOFTCRM 29개 + EICN_MySQL 링크드서버 1개 + IPLUS 링크드서버 1개)
- 모두 **읽기 전용** 접근 (배치가 원천을 수정하지 않음)
- 데이터 이동 방향: 원천 → 배치가 읽음 → Postgres 마트에 적재 → 대시보드 화면이 마트를 조회

## 3. 배치 접근 패턴

| 항목 | 상세 |
|---|---|
| **접근 주기** | 매일 03:00 (전 도메인 · D-1 하루치) · **매일 10:00 (예약통계만 D-1 재실행 — 03:00 이후 늦게 반영된 콜센터·예약 수정분 흡수)** · 매월 1일 03:30 (전월 전체 재조회, 대사용) |
| **참조 빈도** | 그룹 A~E·F 대부분: **하루 1회**. **그룹 F 중 예약통계 원천(HappyTalk_* · RESERVATION · RESERVATION_NAVER · RESERVE_HISTORY · DB_ReCounsel · CtiRptLst · CtiClg · `stat_user_inbound_bseye`(EICN) · DB_CUSTOM · CUSTOM · Cataract_Exam): 하루 2회** (03:00 + 10:00) |

| **드라이버** | JTDS (MSSQL JDBC) |
| **접속** | JDBC 직결 (SOFTCRM 은 공인 IP 직접 · 홈페이지 MariaDB 만 SSH 터널 경유). SOFTCRM 이 EICN_MySQL 과 IPLUS(진료비, 220.85.109.240) 두 링크드서버를 경유해 우회 조회 중 |
| **필터** | 대부분 등록일 / 예약일 컬럼 `BETWEEN :from AND :to` 기간 조회 (전량 스캔 아님) |
| **JOIN 규모** | 크기 다양. 가장 큰 조회는 16개 테이블 JOIN(검사자 리스트) |
| **쓰기 여부** | ❌ 없음 |

- ⚠️ **EICN_MySQL** — SOFTCRM 에 걸린 링크드서버. 실제 MySQL 호스트는 SOFTCRM Windows 서버의 ODBC DSN(`EICN_MySQL_DSN`) 안에 저장. 이관 시 원격 접근권 별도 확보 필요 (§6-2)

## 부록 B. 이관 협의 체크리스트

데이터 플랫폼팀·병원 IT·EICN 벤더·IPLUS 벤더와 협의할 항목을 정리. 이관 실행 전에 아래 항목을 하나씩 확정해야 SQL 재작성 규모·스코프·리스크를 산정할 수 있다.

### B-1. 데이터 공급 방식 (필수 · 데이터 플랫폼팀)

- [ ] **31개 테이블 원본 컬럼명·타입 그대로 공급 가능한지** — 리네이밍·정규화하면 배치 SQL 250여 개가 조용히 깨진다
- [ ] **매일 03:00·10:00 시점에 D-1 데이터가 fresh하게 있는지 SLA 확약** — §3 참조 빈도 참조. 특히 10:00 시점 예약통계 원천이 최신이어야 콜센터 지표 정합 유지
- [ ] **소급 갱신 반영 방식 확정** — `RESERVATION.InsertedDateTime`은 예약 수정 시 갱신, `RESERVE_STATE`는 취소 시 소급 변경. 매일 1회 full snapshot으로는 부족하며 CDC 또는 시간 단위 재수집이 필요
- [ ] **읽기 전용 접근권 계정 발급** — 배치는 SELECT 만 실행 (INSERT/UPDATE/DELETE 없음)

### B-2. 저장 엔진 · SQL 방언 (필수 · 데이터 플랫폼팀)

**데이터 플랫폼의 저장 엔진 유형에 따라 배치 SQL 재작성 규모가 결정된다.**

- [ ] **저장 엔진이 무엇인가**
  - `MSSQL 미러` — 지금 T-SQL 그대로 재활용 가능 (재작성 거의 없음, 접속 URL만 교체)
  - `PostgreSQL` — T-SQL → PL/pgSQL 재작성 필요 (약 60개 SQL, 대략 4~6주 개발 소요)
  - `BigQuery / Snowflake / Databricks` — SQL 대폭 재작성 필요
- [ ] **Babelfish for PostgreSQL 지원 여부** — Postgres가 T-SQL 방언을 이해하도록 하는 AWS 호환 레이어. 사용 가능하면 재작성 대부분 회피
- [ ] **MSSQL 미러 옵션 병행 제공 가능한지** — 배치는 미러 사용, 다른 소비자는 웨어하우스 사용 (자원 부담 있음)

### B-3. 링크드서버 원격 원천 (필수 · 병원 IT · EICN 벤더 · IPLUS 벤더)

현재 SOFTCRM 이 두 원격 서버를 대신 조회 중. 이관 시 두 가지 시나리오 중 선택:

**시나리오 A — 원격 서버도 데이터 플랫폼이 흡수 (SOFTCRM 완전 제거)**
- [ ] **EICN MySQL 실주소·계정 확보** — 현재 SOFTCRM Windows 서버의 ODBC DSN(`HKLM\SOFTWARE\ODBC\ODBC.INI\EICN_MySQL_DSN`)에만 저장. 확인하려면 병원 IT 협조 (`odbcad32.exe`) 또는 EICN 벤더 협의
- [ ] **IPLUS(220.85.109.240) 진료 원무 시스템 접근권 확보** — 4-part name이 실 IP인 것으로 추정되나 실주소·계정은 SOFTCRM `sys.servers` + `sys.linked_logins` 조회로 확인 필요
- [ ] **데이터 플랫폼 서브넷 → EICN·IPLUS 방화벽 라우팅** 개설

**시나리오 B — SOFTCRM 을 링크드서버 브로커로 유지**
- [ ] **SOFTCRM 접속 유지 결정** — 대시보드 완전 탈 SOFTCRM 목표는 미달성 · SOFTCRM 링크드서버 설정 유지·관리 책임자 지정 필요

### B-4. 확장 스코프 결정 (선택 · 별도 협의)

이번 문서에 포함되지 않은 원천도 함께 흡수할지 결정.

- [ ] **홈페이지 MariaDB `TBL_COUNSEL`** — 현재 §5 범위 밖. 흡수하면 예약자 리스트_홈페이지 화면도 데이터 플랫폼으로. 흡수 안 하면 지금처럼 SSH 터널·Bastion(`110.45.179.230:2200`) 유지
- [ ] **EOEIS MSSQL (`dbo.checkup_record`, `dbo.checkup_device_score`)** — 아이리더 검사통계 화면 전용, 배치 아님. 별도 DataSource(`EOEIS_DATASOURCE_URL`)로 접속. 흡수 시 화면 코드도 소폭 변경 필요

### B-5. 배치 SQL 재작성 대비 (내부 준비 · 저장 엔진이 MSSQL 미러가 아닐 경우만)

- [ ] **T-SQL 특유 문법 → 목표 방언 치환** — `WITH(NOLOCK)` · `ISNULL` · `CONVERT(VARCHAR, date, 23)` · `CROSS/OUTER APPLY` · `TOP N` · `[대괄호 식별자]` 등 (약 60개 SQL 파일, 대부분 정규식 치환 가능)
- [ ] **`OPENQUERY` / 4-part name 대체** — 링크드서버 흡수 시 로컬 테이블 참조로. 유지 시 FDW 등으로
- [ ] **CS/CI 콜레이션 감사** — 현재 SOFTCRM은 Korean_Wansung_CI_AS(대소문자 무시). Postgres 등 CS 기본 엔진으로 이관 시 은연중 CI를 가정한 `LIKE`·`=` 비교를 `ILIKE`·`LOWER()`로 감사

### B-6. 운영 이관 계획 (필수)

## 부록 D. 파생 마트 이관 상태 (리스트 기반 vs MSSQL 예외)

리스트 마트 위에 얹혀진 파생·집계 마트가 어떤 방식으로 데이터를 조립하는지 그룹별로 정리. **대부분은 이미 리스트 기반으로 이관 완료(2026-08-19 종결)** 이며, 남은 예외 3개는 정확도·복잡도 trade-off 로 인한 **의도적 MSSQL 직결 유지**.

> 원본 검토 문서: [`docs/db/list-migration-plan.md`](list-migration-plan.md) (2026-08-19 종결)

### 아키텍처 원칙 (2026-08-19 확정)

배치는 2단계로 구성한다:
- **Phase 1** (MSSQL 접근 허용) — primary list(list_*)를 채운다
- **Phase 2** (MSSQL 접근 금지) — 파생 마트는 오직 list 만 읽어 계산

**단, "실시간 판정이 정확도에 결정적인 마트"는 의도적 예외로 MSSQL 유지** (아래 그룹 B·C).

### 그룹 A — 리스트 기반 재집계 · ✅ 이관 완료

MSSQL 안 보고 Postgres 리스트 마트/뷰만 읽어 재집계. **이관 시 원천 SQL 재작성 불필요** — 리스트 마트만 정상 생성되면 자동으로 정상 작동.

| 파생 마트 | 상위 원천 (리스트/뷰) |
|---|---|
| `mart_surgery_monthly` · `mart_surgery_daily` | `v_all_surgery_list` |
| `mart_examination_monthly` · `mart_procedure_exam_monthly` | `v_all_exam_list` |
| `mart_stop_reason_monthly` | `v_all_exam_list` |
| `mart_outpatient_count_monthly` | `list_outpatient` |
| `mart_reservation_monthly` | `list_reservation_all` |
| `mart_exam_count_by_class` | `v_all_exam_list` (2026-08-19 이관) |
| `mart_overall_exam_monthly` · `mart_overall_exam_weekly` | `v_all_exam_list` + `list_exam` (2026-08-19 이관) |
| `mart_weekly_report` (검사·수술·외래·중단 부분) | list 마트들 |

### 그룹 B — 하이브리드 (list 후보 + MSSQL 브릿지) · 🟡 의도적 예외

리스트 마트로 후보를 좁힌 뒤, 검사일 이후 발생한 **미래 예약**을 실시간 판정하려 MSSQL 브릿지 (`ConsultationRateBridgeRepository`) 로 chart_no 청크 조회. 완전 list 이관 시도했으나 정확도 손실(2026-07 vision -125건 사례) 확인되어 하이브리드가 우위.

| 파생 마트 | 왜 브릿지가 필요한가 |
|---|---|
| `mart_consultation_rate_monthly` (전환율) | 검사 → 예약 → 수술 funnel 판정 시 D 당일 예약 gap 을 실시간 조회로 메워야 정확 |
| `mart_reservation_rate_monthly` (예약률) | 상동 |
| `mart_weekly_report` 예약률 4종 | 상동 |

**이관 함의**: 데이터 플랫폼이 실시간(초·분 단위) 정합을 보장한다면 브릿지 없이도 가능. 현재는 배치 스냅샷 gap 을 브릿지로 보정하는 구조.

### 그룹 C — MSSQL 직결 필수 · ❌ 의도적 예외 (이관 부적합)

리스트 마트로 근본적으로 재현 불가하거나, 원천 로직이 특수해서 이관 이득 < 리팩터 비용.

| 파생 마트 | 이관 불가/부적합 근본 원인 |
|---|---|
| `mart_reservation_stats_system_daily` (예약통계 시력교정) | **24채널 중 21채널의 원천이 어떤 list 에도 없음** (CTI · EICN · Naver · HappyTalk 계열). 채널 판정 로직이 CTI 코드체계에 강결합. `RESERVATION.InsertedDateTime` 소급 갱신 실시간 반영 필요 |
| `mart_reservation_stats_cataract_daily` (예약통계 백내장) | 상동. 백내장 특화 채널(new_exam_inquiry·new_re_inquiry 등) 원천도 부재 |
| `mart_b2b_revenue_monthly` (B2B 매출) | `AssignList` (B2B 배정) 가 어떤 list 에도 없음. 비용 소급 재계산(`b2b-latest-cost-subquery.sql`) 이 CUSTOM **현재값** lookup 에 의존 · list 에 이 스냅샷 없음 |

### 그룹 C 를 굳이 리스트화하려면 (참고 · 실무 우선순위 낮음)

기술적으론 가능하지만 신규 리스트 마트 신설과 대규모 리팩터 필요:

- **예약통계** — `list_reservation_channel` + `list_call_stats` + `list_tm_activity` 3종 신규 리스트 필요. CTI 코드 판정 로직을 SQL 밖으로 추출. CDC 로 매 시간 재적재. **공수 2~4주**
- **B2B** — `list_b2b_assignment` (AssignList 이관) + 비용 스냅샷 재설계. **공수 1~2주**

**판단**: 하이브리드·직결 유지가 이미 검증됐고 정확도 우위. 리팩터 비용 대비 이득 낮아 실무 우선순위 낮음.

### 폐지 완료 마트 (참고)

| 마트 | 처리 시기 | 사유 |
|---|---|---|
| `mart_reservation_kakao_daily` | 2026-08-19 폐지 | 프론트가 hook 반환값을 destructure 하지 않음 → dead consumer. 다른 소비처도 없음. SQL·엔드포인트·CREATE 문 제거, 배포 DB 수동 DROP |

### 이관 시 함의 요약

| 그룹 | 이관 방식 | 재작성 SQL |
|---|---|---|
| **A** (리스트 기반) | ✅ 자동 정상 작동 — 리스트 마트만 검증하면 됨 | 0개 (Postgres → Postgres 재집계) |
| **B** (하이브리드) | 데이터 플랫폼이 실시간성 SLA 확약하면 브릿지 제거 가능. 아니면 유지 | 3개 (브릿지 로직 재작성) |
| **C** (MSSQL 직결) | 3가지 옵션 중 선택 필요 | 예약통계 2 + B2B 1 |

**그룹 C 3가지 옵션**:
1. **원천 SQL 만 데이터 플랫폼 방언으로 재작성** — 지금 로직 그대로. 재작성 규모 있음
2. **SOFTCRM 브로커 유지** — 이 3개 마트만 SOFTCRM 계속 사용. 스코프 축소
3. **리스트화 리팩터 병행** — 위 "굳이 리스트화하려면" 참조. 공수 큼

**권장**: 옵션 2 (SOFTCRM 브로커 유지)가 이관 스코프·리스크 관점에서 가장 실용적. 데이터 플랫폼이 성숙한 뒤 옵션 3 을 별개 프로젝트로 진행.

#### 왜 마트가 이미 있는데 브릿지가 필요한가

두 테이블은 이미 `list_reservation_all` · `list_surgery` 마트에 배치로 적재됨. 하지만 **리스트 마트는 배치 target range 로 잘려서 담김**:

- 예: 2026-06 전환율 계산 시 `list_reservation_all` 은 2026-06 데이터만 담음

- 리스트 마트만 조회해서는 이 8월 예약을 못 봄 → 전환율 undercount → -125건 사례

브릿지는 **chart_no 셋의 전체 이력 (range 무관)** 을 MSSQL 라이브에서 가져와 gap 을 메움. 이 작업은 **배치 시점에** 수행되고 결과가 파생 마트(`mart_consultation_rate_monthly` 등)에 저장됨.

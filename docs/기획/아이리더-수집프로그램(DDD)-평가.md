## 1. 평가 범위와 전제

이 문서는 **정종철 님이 만든 원본 아이리더 검사통계 프로그램 MVP 자체**를 평가한다. 현재 프로젝트에 후속으로 구현된 React/Spring 대시보드는 별도 결과물이며, 정종철 님의 MVP 평가 점수에 포함하지 않는다.

평가 목적은 운영 시스템 감사를 통해 결함을 나열하는 것이 아니다. 다음 질문에 답하는 것이 목적이다.

1. 어떤 현장 문제를 발견하고 제품 문제로 정의했는가?
2. 제한된 환경에서 핵심 가설을 검증할 MVP를 얼마나 적절하게 설계했는가?
3. 실제 사용 가능한 결과물까지 구현한 개발 난이도와 완성도는 어느 정도인가?
4. 결과물에서 확인되는 기획·개발 역량은 무엇인가?
5. MVP 검증 이후 제품화 단계에서 무엇을 보완해야 하는가?

현재 전달된 DDD 배포 패키지에는 원본 소스와 빌드 프로젝트가 포함되어 있지 않다. 이는 **현재 자료만으로 내부 코드 품질과 테스트 수준을 평가할 수 없다는 의미**이며, 제작자가 원본 소스를 보유하지 않았다고 단정하는 근거는 아니다.

## 2. 한눈에 보는 최종 평가

이 프로그램은 **현장 업무 문제를 발견하고, 데이터 수집부터 저장·집계·조회·배포까지 하나의 작동하는 제품으로 연결한 완성도 높은 MVP**다.

화면 목업이나 일회성 SQL에 머물지 않고 다음 전체 흐름을 실제로 구현했다.

```text
아이리더 원본 API
    ↓
기간별 데이터 수집
    ↓
중복을 방지하며 MSSQL 저장
    ↓
검사자·장비·일자별 집계
    ↓
건수·가중점수 조회
    ↓
Excel 내보내기와 현장 PC 설치
```

## 3. 이 MVP가 해결한 문제

### 3.1 기존 문제

검사 업무 기록은 아이리더 시스템에 존재하지만 검사실 운영자가 원하는 형태로 바로 보기 어려웠던 것으로 판단된다.

- 검사자별 전체 검사량을 빠르게 비교하기 어렵다.
- 어떤 검사자가 어떤 장비를 주로 사용하는지 파악하기 어렵다.
- 장비별 업무 난이도가 달라 단순 건수만으로 업무량을 보기 어렵다.
- 기간별 통계를 만들려면 데이터를 수작업으로 정리해야 한다.
- 현장 PC마다 실행 환경이 달라 도구 배포가 어렵다.

### 3.2 MVP가 제안한 해결책

- 아이리더 API에서 필요한 기록을 직접 수집한다.
- 자체 MSSQL 테이블에 기록을 축적한다.
- 검사자·장비·일자 단위로 집계한다.
- 검사 건수와 장비 가중 점수를 전환해 본다.
- 오늘 수집과 기간 수집을 구분한다.
- 결과를 Excel로 내보낸다.
- 설치 배치와 자동 업데이트 런처로 현장 배포 비용을 줄인다.

이 선택은 문제와 해결책의 연결이 명확하다. 단순히 “통계 화면을 만들자”가 아니라 **데이터가 어디에 있고, 어떻게 가져오며, 현장에서 어떻게 실행할 것인지**까지 하나의 제품 문제로 다뤘다.

## 4. 기획 의도 평가

### 4.1 핵심 가설

이 MVP가 검증하려 한 가설은 다음과 같이 정리할 수 있다.

> 아이리더 검사기록을 검사자·장비 단위로 자동 집계해 제공하면 검사실의 업무량 파악과 통계 작성 시간을 줄일 수 있다.

보조 가설은 다음과 같다.

- 장비별 가중치를 적용하면 단순 건수보다 업무량을 현실적으로 비교할 수 있다.
- 일일 수집과 기간 재수집을 나누면 평상시 운영과 과거 데이터 보완을 모두 처리할 수 있다.
- 설치와 업데이트를 단순화하면 별도 IT 지원 없이도 현장 도입이 가능하다.

### 4.2 타깃 사용자

| 사용자 | 기대 가치 |
|---|---|
| 검사실 실무자 | 본인과 팀의 장비별 검사량 확인 |
| 검사실 총괄 | 인력·장비별 업무 분포 비교 |
| 관리자 | 누락 기간 재수집, 장비 점수 설정 |
| 운영 담당자 | Excel 자료 생성과 기간별 통계 확인 |

### 4.3 핵심 기능의 기획적 의미

| 기능 | 단순 기능 이상의 의미 |
|---|---|
| 통계 조회 | 저장된 데이터를 의사결정 정보로 변환 |
| 오늘 수집 | 일상 운영을 위한 증분 적재 |
| 기간 수집 | 초기 구축·누락 복구·백필 지원 |
| 검사자 × 장비 | 장비 숙련도와 업무 편중 확인 |
| 검사자 × 일자 | 날짜별 업무량과 변동 확인 |
| 건수/점수 | 물량과 난이도라는 두 관점 제공 |
| 장비 점수 설정 | 현장 기준을 제품에 반영할 수 있는 운영 기능 |
| Excel 내보내기 | 기존 보고·공유 업무와 연결 |

이 기능 구성은 사용자 업무 흐름을 충분히 고민한 결과로 보인다. 특히 수집 기능과 조회 기능을 분리하고, 관리자에게만 수집·점수 관리 기능을 보여주는 구조는 단순 데모를 넘어 실제 사용을 고려한 흔적이다.

## 5. MVP 범위 설정 평가

### 잘한 범위 설정

MVP의 중심을 “검사자별 장비 검사량”에 두고 다음 범위만 구현했다.

- 데이터 수집
- 중복 방지 저장
- 기간 조회
- 두 가지 피벗
- 건수와 가중 점수
- 설정 및 관리자 제어
- Excel 내보내기
- 설치와 업데이트

환자 상세, 복잡한 차트, 조직관리, 결재, 알림 같은 주변 기능을 억지로 넣지 않았다. 핵심 가치를 검증하기에 적절한 범위다.

### MVP임에도 범위가 넓었던 부분

일반적인 MVP라면 화면과 샘플 데이터까지만 구현할 수도 있다. 이 프로그램은 다음까지 포함했다.

- 외부 API 연동
- 실제 DB 적재
- 재수집 시 중복 방지
- 관리자와 일반 사용자 구분
- PC 런타임 설치
- 자동 업데이트 형태의 런처

따라서 단순 화면 MVP가 아니라 **현장 검증이 가능한 엔드투엔드 MVP**다. 개발 난이도와 실행력을 높게 평가할 근거다.

## 7. 기획자 관점에서 잘한 점

### 7.1 현장의 실제 병목을 선택했다

이미 데이터는 존재하지만 업무에 사용할 수 있는 통계로 보이지 않는 문제를 골랐다. 새로운 데이터를 만들기보다 흩어진 데이터를 실무 정보로 바꿨다는 점에서 투자 대비 가치가 높다.

### 7.2 사용자의 다음 행동까지 고려했다

조회만 제공하지 않고 Excel 내보내기를 포함했다. 사용자가 결과를 회의·보고·공유에 활용한다는 점까지 생각한 기능이다.

### 7.3 운영 담당자의 예외 상황을 고려했다

오늘 수집과 기간 수집을 나눈 것은 좋은 기획이다. 일상적 증분 수집과 누락 복구가 서로 다른 업무라는 점을 이해하고 있다.

### 7.4 단순 건수의 한계를 인식했다

장비별 점수를 적용한 것은 모든 검사 1건의 업무 난이도가 같지 않다는 현장 문제를 반영한 것이다. 지표가 완전하지 않더라도 단순 건수보다 나은 의사결정 수단을 시도했다.

### 7.5 도입 장벽도 제품 문제로 봤다

설치와 업데이트를 사용자에게 떠넘기지 않았다. 런타임 자동 설치, 공용 바로가기, 실행 시 갱신은 현장 도입을 제품 범위로 인식했다는 증거다.

### 7.6 기능 욕심을 통제했다

검사자와 장비라는 핵심 축에 집중했다. MVP 단계에서 중요한 “무엇을 하지 않을지”가 비교적 잘 지켜졌다.

## 8. 기획자 관점에서 보완할 점

아래 내용은 MVP의 실패라기보다 **검증 이후 정식 제품으로 발전시키기 위한 다음 단계**다.

### 8.1 성공 기준이 문서화되지 않았다

다음과 같은 목표가 있었다면 MVP 성과를 더 객관적으로 판단할 수 있다.

- 통계 작성 시간 단축
- 월간 수작업 건수 감소
- 데이터 누락률 감소
- 사용자 수와 사용 빈도
- Excel 수작업 보정 건수

### 8.2 지표 정의가 사용자에게 충분히 설명되지 않는다

검사 건수는 환자 수가 아니라 장비 검사 기록 수다. 한 환자가 여러 장비 검사를 받으면 여러 건이 된다. 이 정의가 화면과 내보내기 파일에 명확히 표시되어야 한다.

### 8.3 가중 점수의 운영 원칙이 필요하다

장비 점수는 좋은 아이디어지만 다음 질문에 대한 정책이 필요하다.

- 누가 점수를 정하는가?
- 어떤 근거로 변경하는가?
- 변경된 점수는 과거 통계에도 적용하는가?
- 이 점수를 개인 성과평가에 사용할 수 있는가?

점수는 업무량 참고 지표로 한정하고 단독 인사평가에 사용하지 않는다는 원칙이 필요하다.

### 8.4 데이터 최신성에 대한 약속이 필요하다

수동 실행 중심의 MVP는 초기 검증에는 가능하지만 사용자가 화면을 신뢰하려면 “언제까지의 데이터가 반영됐는지”를 보여줘야 한다.

### 8.5 MVP 종료 조건과 다음 단계가 필요하다

MVP가 유효하다고 판단됐을 때 다음 중 무엇을 할지 정해야 한다.

- 현장 프로그램을 개선해 계속 사용할지
- 자동 수집만 서버로 옮길지
- 조회까지 웹 대시보드로 통합할지

현재 후속 대시보드가 만들어졌다는 것은 MVP가 문제와 수요를 충분히 증명했다는 긍정적인 신호로 볼 수 있다.

## 9. 시니어 개발자 관점에서 잘한 점

### 9.1 엔드투엔드 구현 능력이 확인된다

외부 API, 데이터베이스, 집계, UI, 파일 내보내기, Windows 배포까지 한 제품 흐름으로 연결했다. 한 영역만 구현한 것이 아니라 사용자에게 전달 가능한 수직 기능을 완성했다.

### 9.2 수집의 멱등성을 고려했다

기록 ID를 기준으로 기존 데이터와 비교해 신규 데이터만 저장하는 구조가 확인된다. 같은 날짜를 다시 수집해도 중복되지 않는 특성은 기간 재수집 기능의 필수 조건이다.

제공된 로그에서도 `수신 52건 / 신규 저장 0건` 사례가 확인된다. 이는 최소한 해당 실행에서 중복 방지가 작동했다는 근거다. 전체 운영 이력을 의미하지는 않는다.

### 9.3 재집계하기 좋은 데이터 단위를 선택했다

검사자·장비·일자 단위의 세밀한 집계를 사용하므로 검사자×장비와 검사자×일자를 같은 데이터에서 만들 수 있다. 건수와 점수도 화면에서 빠르게 전환할 수 있다.

### 9.4 설정을 실행 파일 밖으로 분리했다

API 주소, 페이지 크기, 타임아웃, DB 연결정보, 대상 테이블 등을 `config.ini`에 분리했다. 환경 변화에 대응하기 위해 실행 파일을 다시 만들 필요를 줄였다.

### 9.5 현장 배포 문제를 기술적으로 해결했다

- 관리자 권한 자동 승격
- ODBC 드라이버 확인과 설치
- WebView2 런타임 확인과 설치
- 로컬 실행 폴더 구성
- 공용 바탕화면 바로가기 생성
- 실행 시 최신 실행 파일 복사

개발자가 자신의 PC에서 실행하는 데 그치지 않고 실제 사용자 PC에서 실행되는 조건까지 해결했다는 점은 높은 실행력의 증거다.

### 9.6 사용자 권한 개념을 MVP에 포함했다

관리자 모드에서 수집 버튼을 제공하고 장비 점수 변경을 잠금 처리한 것은 모든 기능을 무제한으로 노출하지 않으려 한 설계다. 정식 권한 모델은 아니어도 운영 역할을 인식하고 있었다.

## 10. 시니어 개발자 관점에서 보완할 점

### 10.1 DB 관리자 계정 사용은 즉시 개선해야 한다

현재 배포 설정은 SQL Server 관리자 계정을 사용한다. 비밀번호 난독화는 평문 노출을 줄일 뿐 강한 비밀정보 보호가 아니다.

MVP 검증 이후에는 반드시 다음처럼 분리해야 한다.

| 계정 | 최소 권한 |
|---|---|
| 수집 계정 | 대상 기록 테이블 SELECT·INSERT |
| 조회 계정 | 통계 테이블 SELECT |
| 점수 관리 | 점수 테이블에 필요한 제한적 변경 권한 |

이 문제는 MVP의 핵심 아이디어를 훼손하지 않지만 운영 사용을 계속하기 전에는 해결해야 하는 P0 기술부채다.

### 10.2 전송 보안과 API 인증을 확인해야 한다

정적 분석에서 HTTP 사용 가능성이 확인되지만 실제 네트워크 경로, 접근 제한, 인증 방식은 현재 자료만으로 확정할 수 없다. 벤더와 함께 HTTPS·인증·VPN 또는 전용망 여부를 확인해야 한다.

### 10.3 자동 업데이트 무결성 검증이 필요하다

공유 위치의 실행 파일을 복사해 실행하는 방식은 간단하고 실용적이지만 파일 서명·해시·버전·롤백이 없다. 정식 운영 단계에서는 변조와 잘못된 배포를 막는 장치가 필요하다.

### 10.4 수집을 사람의 실행에 의존하지 않게 해야 한다

현재 전달 패키지 안에서는 자동 스케줄링 기능이 확인되지 않는다. 외부 작업 스케줄러가 별도로 구성됐는지는 추가 확인이 필요하다.

MVP 검증 후에는 다음 중 하나가 필요하다.

- Windows 작업 스케줄러 등록
- 서버 스케줄러 또는 Spring Batch 이관
- 실패 시 중앙 알림과 재시도

### 10.5 중앙 로그와 상태 관리가 필요하다

로컬 `collect.log`만으로는 어느 PC에서 수집했는지, 마지막 성공 시각이 언제인지, 누락 날짜가 있는지 알기 어렵다. 수집 실행 이력과 마지막 원본 날짜를 중앙에서 관리해야 한다.

### 10.6 소스·빌드·테스트 인수인계 상태를 확인해야 한다

현재 DDD 배포본에는 원본 소스, 의존성 목록, 빌드 명령, 테스트가 포함되어 있지 않다. 다음 자료가 별도로 존재하는지 제작자에게 확인해야 한다.

- 원본 저장소
- Python 및 라이브러리 버전
- PyInstaller 빌드 설정
- 테스트 또는 검증 시나리오
- 버전 이력
- 장애 대응과 배포 절차

이 자료가 별도로 존재한다면 유지보수 평가 점수는 올라갈 수 있다.

### 10.7 안정적인 설치 실패 처리가 필요하다

설치 구성요소나 실행 파일 복사에 실패했을 때 설치를 중단하고 원인을 명확히 알려야 한다. 버전 표시, 제거 스크립트, 로컬 설정 캐시도 정식 배포 단계에서 보완할 부분이다.

## 11. 정종철 님의 기획 역량 평가

### 결과물에서 확인되는 강점

| 역량 | 평가 근거 |
|---|---|
| 현장 문제 발견 | 기존 데이터가 업무 정보로 활용되지 않는 문제를 선택 |
| 사용자 흐름 설계 | 수집→조회→설정→내보내기의 업무 흐름 구성 |
| MVP 우선순위 | 검사자·장비 업무량이라는 핵심 문제에 집중 |
| 운영 예외 고려 | 오늘 수집과 기간 수집, 관리자 모드 포함 |
| 도입 전략 | 설치와 업데이트 부담까지 제품 문제로 해결 |
| 확장 가능성 | 세밀 데이터 구조로 다양한 통계 전환 가능 |

### 기획자로서의 평가

정종철 님은 요구받은 화면만 구현한 것이 아니라 **데이터 확보부터 현장 사용까지 전체 사용자 여정을 제품 범위로 정의했다.** 이는 기획 문서를 잘 작성하는 능력과 별개로, 실제 문제를 작동하는 기능으로 번역하는 실무형 기획 역량이 있다는 근거다.

보완할 부분은 성공지표, 데이터 최신성 SLA, 점수 운영 원칙, 제품 수명주기와 같은 제품화 단계의 정책 설계다.

> **기획 역량 평가: 8.5/10 — 현장 문제를 빠르게 구조화하고 MVP 범위를 현실적으로 결정하는 능력이 강하다.**

### 결과물에서 확인되는 강점

| 통합 구현 | API·DB·UI·Excel·Windows 배포를 연결 |
| 데이터 처리 | 페이징, 기간 수집, 중복 방지, 집계 구현 |

따라서 산출물 하나만으로 개발자의 전체 시니어리티를 확정할 수는 없다. 그러나 **한 사람이 현장 문제를 엔드투엔드 제품으로 완성하는 실행력**은 분명하게 확인된다.

보완할 부분은 최소권한 보안, 배포 무결성, 자동 스케줄링, 중앙 모니터링, 재현 가능한 빌드와 인수인계다.

> **개발 역량 평가: 8.0/10 — 빠른 프로토타이핑을 넘어 실제 사용 가능한 수직 제품을 완성하는 실무형 개발 역량이 강하다.**

## 13. MVP 성과와 제품화 기술부채의 구분

| 항목 | MVP 단계 평가 | 제품화 단계 판단 |
|---|---|---|
| 수동 수집 | 초기 검증에는 수용 가능 | 자동화 필요 |
| 로컬 실행 프로그램 | 현장 접근 제약 해결 | 서버 수집으로 이전 권장 |
| 장비 점수 | 업무량 가설 검증에 유효 | 버전·근거·변경이력 필요 |
| 관리자 비밀번호 | 역할 구분 개념 검증 | 통합 인증·권한 필요 |
| 공유 위치 업데이트 | 빠른 배포에 효과적 | 서명·해시·롤백 필요 |
| DB 관리자 계정 | 기능 검증은 가능 | 즉시 최소권한으로 교체해야 함 |
| 로컬 로그 | 초기 확인 가능 | 중앙 이력·알림 필요 |

이 구분이 중요하다. 제품화 요건이 부족하다는 이유만으로 MVP의 문제정의와 실행력을 낮게 평가해서는 안 된다. 반대로 MVP였다는 이유로 확인된 보안 위험을 계속 허용해서도 안 된다.

## 14. 후속 대시보드 구현이 의미하는 것

원본 MVP의 조회 기능이 현재 React/Spring 대시보드 메뉴로 다시 구현된 것은 다음을 의미한다.

1. 원본 MVP가 해결한 문제가 일회성이 아니었다.
2. 실제 데이터와 사용 가치가 있었기 때문에 조직 시스템으로 확장됐다.
3. 원본 MVP가 요구사항 탐색과 업무 규칙 확인의 기준점 역할을 했다.
4. 화면 구조, SQL, 제외 규칙, 점수 개념을 후속 구현에서 참고할 수 있었다.

따라서 후속 대시보드는 원본 MVP의 실패를 고친 결과라기보다 **MVP가 검증한 가치를 조직용 시스템으로 확장하는 다음 단계**로 보는 것이 타당하다.

다만 후속 React/Spring 코드의 품질과 구현 성과는 별도 개발 작업이므로 정종철 님의 원본 MVP 평가에 합산하지 않는다.

## 15. 권장 다음 단계

### 즉시 확인

- DB 관리자 계정을 최소권한 계정으로 교체하고 기존 비밀번호를 변경한다.
- DDD 배포 위치의 접근 권한을 제한한다.
- 원본 소스 저장소와 빌드 문서의 보유 여부를 정종철 님에게 확인한다.
- 실제 수집 주기와 담당자를 확인한다.
- API의 HTTPS·인증·네트워크 접근제한을 확인한다.

### 단기 개선

- 마지막 수집 시각과 최신 데이터 날짜를 대시보드에 표시한다.
- 자동 일일 수집과 실패 알림을 구성한다.
- 점수 변경 주체와 기준을 문서화한다.
- 검사 건수가 환자 수가 아니라 장비 검사 기록 수임을 명시한다.

### 중기 제품화

- 수집 로직을 서버 배치로 이관한다.
- 조회 화면은 Postgres 통계 마트를 읽도록 전환한다.
- 기간 백필, 재시도, 실행 이력을 관리한다.
- 점수에 적용기간·변경자·변경 사유를 추가한다.
- 서버 전환이 안정화되면 DDD 프로그램의 역할과 종료 시점을 확정한다.

## 16. 최종 총평

정종철 님의 아이리더 검사통계 프로그램은 **현장 문제를 정확히 발견하고, 실제 데이터와 사용자 환경을 연결해 빠르게 검증한 좋은 MVP**다.

특히 높게 평가할 부분은 다음과 같다.

- 화면만 만든 것이 아니라 데이터 수집부터 시작했다.
- 반복 수집을 고려해 중복을 방지했다.
- 건수와 장비 점수라는 두 가지 업무 관점을 제시했다.
- 관리자와 일반 사용자의 역할 차이를 반영했다.
- 설치와 업데이트까지 직접 해결해 현장 사용 가능한 상태로 마무리했다.

보안·자동화·모니터링·인수인계는 제품화 단계에서 보완해야 한다. 그러나 이것을 이유로 원본 MVP의 방향과 성과를 낮게 평가하는 것은 적절하지 않다.

> **한 줄 평가: 정종철 님은 아이디어를 제시하는 데 그치지 않고, 현장의 실제 데이터를 수집해 사용자가 실행할 수 있는 프로그램으로 완성했다. 제품화 보완점은 있지만, MVP 기획력과 엔드투엔드 개발 실행력은 높게 평가할 수 있다.**

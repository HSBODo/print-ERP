수술 후 안내 문자(알림톡·SMS) 1~3차 발송과 점검 · 관리자 전용 · 2026-08-07
1

개요와 목적

무엇을 하는 화면인가

수술을 마친 환자에게 정해진 간격으로 안내 문자를 자동 발송하고, 그것이 제대로 나갔는지 점검하는 화면이다.

핵심 전제

  • 발송은 자동화가 한다. 화면은 발송 버튼을 누르는 곳이 아니라 결과를 확인하고 예외를 막는 곳이다.
  • 대상은 마트(list_surgery)에서 자동 등록된다. 수술한 사람이면 자동으로 목록에 들어온다.
  • 사람이 개입해야 하는 경우는 셋뿐이다 — 연락처가 틀렸을 때 · 보내면 안 될 사람일 때 · 마트에 없는 사람을 추가할 때.

접근 권한

ADMIN 전용이다. 환자 연락처를 다루므로 일반 사용자에게 노출하지 않는다.

2

발송 정책 — 1~3차

차수코드발송 시점기본 라벨
1차T1기준일 +7일수술 후 안내 1차
2차T2기준일 +14일수술 후 안내 2차
3차T3기준일 +21일수술 후 안내 3차

간격은 SOLAPI_INTERVAL_DAYS(기본 7)의 배수다. 수술 종류(시력교정·백내장·재수술)와 무관하게 같은 간격을 쓴다.

채널 우선순위

알림톡(ATA)→ 실패 시 →문자(SMS/LMS)

알림톡 템플릿 ID와 문자 본문을 둘 다 설정하면 알림톡을 먼저 보내고 실패하면 문자로 대체발송된다. 한쪽만 설정하면 그 채널만 쓴다.

설정 미완료 경고

어떤 차수에 알림톡 ID와 문자 본문이 모두 비어 있으면 그 차수는 보낼 내용이 없어 자동 발송이 실패한다. 화면 상단에 ⚠️ 설정 미완료: 1차 · 2차 · 3차 로 경고한다.

기준일(scheduleBase) — 예정일을 세는 시작점

보통은 수술일과 같다. 다만 연락처를 못 고친 채(또는 홀딩된 채) 예정일이 지나버리면 그 차수는 영영 나가지 않는다. 그래서 연락처를 고치거나 홀딩을 풀 때 기준일을 다시 깐다 — 안 보낸 차수 중 가장 이른 것이 오늘이 되도록 밀고, 나머지 차수는 원래 간격을 유지한다.

기준일이 수술일과 다른 행은 재조정됨으로 표시해, 왜 간격이 달라 보이는지 알 수 있게 한다.

상태 정의

상태는 사람 기준이며, 아래 우선순위대로 판정한다. 위에서 먼저 걸리면 아래는 보지 않는다.

상태판정 조건뜻되돌리기
발송 불가연락처가 없거나 더미보낼 방법이 없다. 데이터 문제불가 — 연락처를 고쳐야 함

발송발송 이력이 1건 이상한 번이라도 보낸 사람—
발송 대기위 어디에도 해당 없음아직 안 보낸 사람—

연락처 유효성 — '발송 불가' 판정

번호를 모를 때 자리만 채우는 관행이 있어 더미 번호가 섞여 들어온다. 아래는 발송 불가로 본다.

  • 빈 값 · 형식 오류
  • 국번 뒤가 같은 숫자로만 채워진 값 (01000000000, 01011111111 …)
왜 거르는가

더미 번호로 발송하면 비용은 나가고 도달은 안 되며, 최악의 경우 무관한 사람에게 환자 안내가 간다. 화면에서 미리 빨간색으로 드러내 손대게 한다.

홀딩(HOLD)의 성격

삭제가 아니라 발송 제외다. 대상 행은 남기고 발송에서만 뺀다. 컴플레인·수신거부 등에 쓰며 언제든 되돌릴 수 있다. 이력을 남겨야 하므로 지우지 않는다.

6

차수 칸 색 규칙

1·2·3차 칸은 날짜(MM-DD) 하나와 색 하나로 상태를 나타낸다. 색이 곧 의미다.

표시조건날짜의 뜻읽는 법
진한 검정발송 성공 + 도달 확인실제 도달일정상 — 확인 끝
주황발송했으나 도달 미확인발송일결과 대기 중 (자동화가 채운다)
빨강발송 실패 또는 예정일 경과 후 미발송발송일 / 예정일점검 대상
회색아직 예정일 전발송 예정일정상 — 기다리면 됨
회색 취소선홀딩 또는 발송 불가예정일보내지 않음
—수술일·기준일 없음—데이터 미비
빨강 두 가지를 같은 색으로 두는 이유

발송 실패와 예정일이 지났는데 안 나감은 원인이 다르지만 둘 다 사람이 봐야 하는 칸이다. 색을 나누면 "어느 쪽이 더 급한가"를 매번 판단해야 해서, 점검 필요 하나로 묶었다. 구체적 사유는 툴팁에 있다.

툴팁에 담기는 것

  • 도달 시각 · 발송 시각
  • 요청 채널(알림톡/문자)과 대체발송 여부
  • 실패 사유
  • 예정일 (미발송·제외 칸)

자동 등록 갱신 규칙

  • AUTO 행은 동기화 때 CRM 최신값으로 갱신된다 — 연락처의 정답은 CRM이기 때문.
  • 단 상태(홀딩 여부)와 메모는 건드리지 않는다 — 사람의 판단을 덮으면 안 된다.
  • MANUAL 행은 갱신하지 않는다. 사람이 고친 값이 우선이다.

9

외부 연동 — 솔라피(SOLAPI)

발송은 우리 백엔드가 솔라피 SDK 1.0.3으로 직접 수행한다. 프론트가 외부로 직접 나가지 않는다.

발송 후 상태가 확정되는 순서

PENDING→ SENDING→ COMPLETE / FAILED
발송 직후 값은 결과가 아니다

발송 API 응답은 "솔라피가 접수했다"까지다. 실제 도달 결과는 통신사 회신 후 수 분~수십 분 뒤 확정된다. 따라서 재조회 배치가 필수이며, 그 전까지 차수 칸은 주황(미도달)으로 남는다.

솔라피에서 가져올 수 있는 값

필드뜻사용
status / statusCode발송 상태·결과 코드사용 — 성공/실패 판정
dateReceived단말 수신 시각사용 — delivered_at
replacement / replacements대체발송 여부·실제 메시지사용 — replacement

읽음·열람은 확인할 수 없다

SMS·알림톡은 규격 자체에 읽음 확인이 없다. 카카오도 읽음 확인 API를 제공하지 않으며, SDK에 해당 필드가 존재하지 않는다. 확인 가능한 최대치는 단말 도달(dateReceived)까지다.

반응을 측정하려면 본문에 자사 도메인 단축 URL을 넣고 접속을 직접 로깅하는 방법뿐이다.

자동화

작업주기내용
대상 적재일 1회마트에서 신규 수술자를 대상으로 등록, AUTO 행 CRM 값 갱신
차수 발송일 1회예정일이 도래한 차수를 발송. 홀딩·발송 불가는 자동 제외
결과 재조회일 1회 (D-1)솔라피 getMessageList로 도달 여부를 회수해 status·delivered_at·replacement 갱신

화면의 발송 버튼은 예외 처리용이다 — 자동 발송이 실패했거나 수동으로 추가한 대상을 보낼 때 쓴다.

환경 설정

시크릿이므로 backend/.env(gitignored)에 둔다. 변경 후 서버 재시작해야 반영된다.

키설명
SOLAPI_API_KEY / SOLAPI_API_SECRET솔라피 인증
SOLAPI_FROM발신번호 (사전 등록 필요)
SOLAPI_PFID카카오 채널 ID (알림톡용)
SOLAPI_TPL{1,2,3}_LABEL차수 라벨
SOLAPI_TPL{1,2,3}_ID알림톡 템플릿 ID
SOLAPI_TPL{1,2,3}_SMS문자 본문
SOLAPI_INTERVAL_DAYS차수 간격 (기본 7)

차수당 알림톡 ID 또는 문자 본문 중 하나 이상을 채워야 그 차수가 동작한다.

12

제약과 미결

구조적 제약 — 바꿀 수 없는 것

  • 읽음·열람 측정 불가. 도달까지가 한계다.
  • 발송 직후 결과 미확정. 재조회 전까지 주황(미도달)으로 남는다.
  • 당일 수술은 조회되지 않는다. 마트 적재가 D-1이라 기본 조회일이 어제다.

미결 — 정해야 할 것

  • 재발송 정책. 실패한 차수를 자동으로 다시 보낼지, 사람이 판단할지 정해지지 않았다.
  • 수신거부 처리. 현재는 수동 홀딩뿐이다. 080 수신거부 연동은 미구현.
  • 수술 종류별 문구 분기. 지금은 차수만 다르고 종류별 문구는 같다.
  • 발송 비용 집계. 솔라피가 제공하지만(GroupLog.totalPrice) 저장하지 않는다.
  • 링크 클릭 측정. 유일한 반응 지표가 될 수 있으나 미구현.

# 아이리더 검사통계 프로그램 기획·개발 평가

> **평가 범위 안내:** 이 문서는 원본 DDD 프로그램을 기반으로 후속 구현된 React/Spring 대시보드의 제품화 준비도를 평가한다. 정종철 님이 제작한 원본 MVP 자체에 대한 평가는 [`아이리더-수집프로그램(DDD)-평가.md`](아이리더-수집프로그램(DDD)-평가.md)를 기준으로 하며, 두 결과물의 개발 성과를 혼합해 평가하지 않는다.

- 작성일: 2026-08-04
- 평가 대상: 대시보드의 `아이리더 검사통계` 메뉴와 원본 EoeisStats 레거시 프로그램
- 평가 관점: 제품 기획, 데이터 정의, 프론트엔드, 백엔드, 보안, 운영
- 평가 기준: 현재 코드, 레거시 정적 분석, 2026년 7월 실데이터 조회 결과

## 1. 결론 요약

현재 구현은 **레거시 프로그램의 핵심 조회 기능을 웹 대시보드로 옮긴 조회형 MVP**로는 성공적이다. 설치 파일이 보안 프로그램에 의해 삭제되는 문제를 피하면서, 검사자별 장비 사용량을 중앙 화면에서 조회·정렬·내보낼 수 있게 한 사용자 가치는 분명하다.

다만 현재 상태를 **레거시 프로그램의 완전한 대체품**으로 정의하면 과대평가다. 레거시의 주요 운영 기능인 데이터 수집, 공용 장비 점수 저장, 관리자 권한, 데이터 최신성 관리가 아직 빠져 있다. 특히 현재 연동 계정이 SQL Server `sa`라는 점과 수집 기능이 레거시에 의존한다는 점은 운영 전 반드시 해결해야 한다.

## 2. 기획 의도 해석

이 프로그램의 본질은 단순한 검사 건수 조회가 아니다. 다음 세 가지 문제를 동시에 해결하려는 운영 도구다.

1. 검사자가 어떤 장비를 얼마나 사용했는지 파악한다.
2. 장비별 업무 난이도 또는 가중치를 반영해 단순 건수 외의 환산 점수를 본다.
3. 여러 PC에 설치되는 로컬 프로그램 대신 중앙 대시보드에서 동일한 데이터를 공유한다.

### 기대 사용자

- 검사실 실무자: 본인과 팀의 검사량 확인
- 검사실 총괄: 검사자·장비별 업무 분포 확인
- 관리자: 장비 가중치 관리, 누락 기간 재수집, 운영 상태 점검
- 경영·운영 담당자: 인력 배치와 장비 활용도 판단

### 핵심 질문

이 화면은 아래 질문에 답해야 한다.

- 특정 기간에 검사실에서 총 몇 건의 장비 검사가 수행됐는가?
- 검사자별 업무량은 어떻게 분포하는가?
- 특정 장비가 일부 검사자에게 편중됐는가?
- 날짜·주차·월 단위로 업무량이 어떻게 변했는가?
- 장비 난이도를 반영하면 환산 업무량은 어떻게 달라지는가?

현재 구현은 첫 네 질문에는 상당 부분 답하지만, 마지막 질문은 점수 기준의 통제와 이력 관리가 없어 참고용 수준이다.

## 3. 현재 수치가 의미하는 것

2026-07-01부터 2026-07-31까지 검증된 화면 합계는 `22,180건`이다.

| 구분 | 건수 | 의미 |
|---|---:|---|
| 원본 검사 기록 | 22,367 | 기간 내 `checkup_record` 장비 검사 기록 |
| KD·LS 계정 제외 | -187 | 레거시 규칙에 따른 원장 계정 제외 |
| 최종 표시 건수 | 22,180 | 화면에 표시하는 장비 검사 기록 수 |
| 검사자 미지정 | 2,115 | NULL·빈 문자열·공백 검사자 기록을 통합한 값 |

이 수치는 **환자 수가 아니라 장비 검사 기록 수**다. 한 환자가 여러 장비로 검사받으면 여러 건으로 계산된다. `[검사]`, `[어시]`, `[진료부]`는 개인 검사자의 소계가 아니라 DB에 실제 검사자명으로 저장된 공용 계정이다.

따라서 화면과 CSV에는 다음 설명이 상시 노출되는 것이 좋다.

> 검사 건수는 환자 수가 아닌 장비별 검사 기록 수입니다. 한 환자의 복수 장비 검사는 각각 집계됩니다.

### 세 버튼의 정확한 역할

- `통계 조회`: 이미 MSSQL에 저장된 데이터를 읽는다. 외부 아이리더 API에서 새 데이터를 가져오지 않는다.
- `오늘 수집`: 보통 당일 또는 설정된 최근 하루 데이터를 아이리더 API에서 받아 신규 기록만 저장하는 증분 수집이다.
- `기간 수집`: 장애 복구나 과거 누락 보완을 위해 기간을 하루씩 나누어 재수집하는 백필 기능이다.

따라서 현재 `통계 조회`가 성공한다고 데이터가 최신이라는 보장은 없다. 수집 주체와 마지막 수집 시각이 별도로 필요하다.

| 영역 | 난이도 | 이유 |

### MVP와 완성형의 난이도 차이

- 현재 조회형 MVP: 약 4/5
- 자동 수집과 운영 관리까지 포함한 완성형: 약 5/5

수집 버튼 두 개를 단순 API 호출로 붙이면 기능은 빨리 보일 수 있지만, 중복·재시도·장시간 실행·진행률·권한 문제 때문에 운영 품질은 낮아진다. 기간 수집은 특히 브라우저의 동기 요청이 아니라 백그라운드 작업으로 설계해야 한다.

## 6. 시니어 개발자 관점의 장점

### 6.1 개인정보 최소화가 잘 되어 있다

통계 SQL은 `patient_no`와 `checkup_record_id`를 조회하지 않고 검사자명·장비명·날짜·건수만 반환한다. 대시보드에 환자 식별정보를 전달하지 않는 것은 좋은 설계다.

### 6.2 원본 데이터를 세밀한 단위로 받아 프론트에서 유연하게 피벗한다

API가 검사자·장비·일자 단위의 희소 집계 행을 반환하므로 검사자×장비, 검사자×기간, 건수, 점수를 빠르게 전환할 수 있다. 현재 데이터 규모에서는 구현이 단순하고 반응성이 좋다.

### 6.3 전용 데이터소스로 장애를 격리했다

EyeReader 연결을 별도 Hikari 풀로 구성하고 URL이 없으면 관련 서비스만 비활성화한다. 외부 DB 문제로 전체 대시보드가 시작되지 않는 상황을 줄였다.

### 6.4 기간 파라미터를 바인딩한다

SQL 문자열 결합 없이 `:from`, `:toExclusive`를 사용한다. 종료일 다음 날 미만 조건으로 시각이 있는 데이터도 종료일 전체가 포함된다.

### 6.5 레거시와 다른 부분을 사용자 요구에 맞게 개선했다

NULL·빈 문자열·공백 검사자를 `(검사자 미지정)` 한 행으로 합쳤고, KD/LS 제외 규칙과 기본 이름 정렬을 재현했다. 단순 복제가 아니라 사용성 개선이 반영됐다.

### 6.6 UI 기본기가 좋다

- 전체 합계는 페이지와 무관하게 전체 행 기준으로 계산된다.
- 정렬 후 페이지네이션이 적용된다.
- CSV는 현재 페이지만이 아니라 정렬된 전체 행을 내보낸다.
- 고정 검사자 열과 고정 헤더가 넓은 피벗 테이블에 적합하다.
- `aria-sort`, 실제 라디오 입력, 입력 라벨 등 접근성 기반이 있다.

## 7. 시니어 개발자 관점의 단점과 위험

### 7.1 치명적: 운영 DB에 `sa` 계정을 사용한다

현재 레거시에서 이관한 계정은 SQL Server `sa`다. Hikari의 `readOnly=true`는 애플리케이션 힌트일 뿐 DB 권한 통제가 아니다. 애플리케이션 취약점이나 설정 오류가 발생하면 EyeReader 전체 DB가 위험해질 수 있다.

권장 분리는 다음과 같다.

| 계정 | 권한 |
|---|---|
| `eoeis_dashboard_reader` | 두 통계 테이블 SELECT 전용 |
| `eoeis_collector` | 수집 대상 테이블 SELECT·INSERT에 필요한 최소 권한 |
| 점수 관리 계정/API | 점수 테이블에 한정된 SELECT·UPDATE와 감사로그 |

조회 기능을 위해 수집 권한까지 가진 계정을 공유해서는 안 된다.

### 7.2 높음: 수집이 빠져 데이터 최신성을 보장하지 못한다

현재 화면은 DB를 잘 읽지만 DB를 갱신하지 않는다. 레거시 프로그램이나 별도 작업이 멈추면 화면은 정상처럼 보이면서 오래된 수치를 표시한다. 이는 연결 오류보다 발견하기 어려운 운영 장애다.

최소한 다음 정보를 제공해야 한다.

- 마지막 원본 검사일
- 마지막 수집 시각
- 마지막 수집 성공·실패 상태
- 수신 건수와 신규 저장 건수
- 지연 시간이 허용 기준을 넘었을 때 경고

### 7.3 높음: 점수의 재현성과 권한이 없다

현재 점수 변경은 브라우저 메모리에만 적용되고 새로고침하면 초기화된다. 같은 기간을 조회해도 사용자마다 다른 점수와 CSV가 만들어질 수 있다.

또한 현재 방식처럼 “현재 점수 × 과거 건수”로 계산하면 장비 점수를 변경하는 순간 과거 점수도 달라진다. 평가 자료로 사용하려면 점수 버전과 적용 기간이 필요하다.

권장 필드 예시는 다음과 같다.

- 장비 식별자
- 점수
- 적용 시작일·종료일
- 변경자
- 변경 시각
- 변경 사유

### 7.4 높음: 이름을 식별자로 사용한다

검사자는 `operator_nm`, 장비는 `checkup_kind_nm`으로 묶인다. 동명이인은 합쳐지고 이름을 변경한 사람은 분리된다. 장비 명칭 변경도 과거와 현재를 별도 장비로 만들 수 있다.

장기적으로 `operator_id`, `checkup_kind_id`를 집계 키로 사용하고 이름은 표시값으로 사용해야 한다. KD/LS 제외도 이름 문자열 검색이 아니라 명시적인 계정 분류 또는 제외 목록으로 관리하는 편이 안전하다.

### 7.5 중간: 1년 조회와 동시 사용에 대한 성능 근거가 부족하다

현재는 DB에서 일자 단위로 집계한 뒤 모든 결과를 한 번에 내려준다. 데이터가 커지면 응답 크기와 프론트 피벗 비용이 증가한다.

추가 확인이 필요한 항목은 다음과 같다.

- `record_begin_dt` 인덱스 존재 여부
- 366일 조회 실행 계획
- 5~20명 동시 조회 부하
- SQL 실행 제한시간
- 응답 행 수 및 전송 크기

현재 연결 풀 최대값 2는 DB 보호에는 유리하지만 동시 사용자가 늘면 대기 병목이 될 수 있다. 연결 제한과 쿼리 제한시간을 함께 측정해야 한다.

### 7.6 중간: 프론트와 백엔드 제약이 중복된다

최소 조회일 `2026-07-01`이 프론트와 백엔드에 각각 하드코딩되어 있다. 변경 시 한쪽만 수정될 수 있다. 최대 기간은 백엔드에만 있어 사용자는 요청 후에야 실패를 알게 된다.

또한 현재 최대 기간 검증은 날짜 차이가 366일까지 허용되어 시작일과 종료일을 모두 세면 최대 367개 날짜가 될 수 있다. 업무 정의가 “포함일 기준 366일”인지 명확히 정해야 한다.

### 7.7 중간: 테스트가 UI 표시와 SQL 문자열 검증에 치우쳐 있다

현재 장점은 핵심 화면 테스트와 개인정보 컬럼 제외 테스트가 있다는 것이다. 그러나 다음 검증은 빠져 있다.

- 실제 MSSQL 또는 호환 환경의 Repository 통합 테스트
- 데이터소스 미설정 시 503 테스트
- 최소일·최대 기간 Controller 테스트
- 월 경계·연도 경계·주차 경계 피벗 테스트
- 점수 버전 및 반올림 정책 테스트
- CSV 내용과 한글 호환성 테스트
- 장기간·동시 조회 성능 테스트

### 7.8 중간: 레거시 드라이버와 운영 관측성이 약하다

jTDS 연결은 현재 동작하지만 장기적인 TLS·SQL Server 호환성 검토가 필요하다. 신규 구축이라면 Microsoft SQL Server JDBC 드라이버 전환을 검토할 가치가 있다.

현재 로그로 연결 성공은 확인할 수 있지만 EOEIS 전용 헬스체크, 조회 시간, 실패율, 마지막 성공 조회 같은 운영 지표가 없다.

### 7.9 낮음: 화면 파일이 커지고 책임이 집중되어 있다

`EoeisCheckupStatsPage.tsx`는 약 456줄로 프로젝트의 500줄 기준에 근접한다. 날짜 그룹, 피벗 계산, 점수 패널, 테이블, 페이지 상태가 한 파일에 있다.

다음 정도로 분리하면 테스트와 변경이 쉬워진다.

- `eoeisPivot.ts`: 날짜 그룹·피벗 계산
- `EoeisStatsToolbar.tsx`
- `EoeisStatsTable.tsx`
- `DeviceScorePanel.tsx`

## 8. 기획자 관점의 장점

### 8.1 사용자 문제와 해결책이 직접 연결된다

로컬 설치 파일이 보안 정책으로 삭제되는 문제를 웹 화면으로 전환해 해결했다. 사용자는 설치·업데이트 없이 대시보드 로그인만으로 이용할 수 있다.

### 8.2 한 화면에서 다양한 관점을 전환할 수 있다

검사자×장비와 검사자×기간을 제공하고 일·주·월 단위를 선택할 수 있어 운영 회의와 개인 확인에 모두 활용할 수 있다.

### 8.3 기존 업무 화면과 유사해 도입 저항이 낮다

레거시의 날짜, 조회, 건수/점수, 장비 점수, 피벗 구조를 유지했다. 완전히 새로운 UI보다 교육 비용이 낮다.

### 8.4 설치형 도구보다 조직 공유가 쉽다

같은 URL과 데이터 기준을 사용하므로 특정 PC에 종속되지 않는다. 메뉴 권한, 사용 로그, 배포를 중앙 관리할 기반도 생겼다.

### 8.5 미지정 검사자를 숨기지 않는다

누락 데이터를 버리지 않고 `(검사자 미지정)`으로 표시해 데이터 품질 문제를 운영자가 발견할 수 있다.

## 9. 기획자 관점의 단점과 위험

### 9.1 제품의 성공 기준이 정의되어 있지 않다

현재 화면이 무엇을 개선해야 성공인지 측정 기준이 없다. 예시는 다음과 같다.

- 레거시 실행 횟수 90% 감소
- 수집 지연 30분 이내
- 미지정 검사자 비율 2% 이하
- 월간 통계 작성 시간 1시간에서 10분으로 단축
- CSV 수작업 보정 건수 0건

### 9.2 “검사 건수”가 환자 수로 오해될 수 있다

실제 수치는 장비 검사 기록 수다. 이 정의를 모르면 경영 지표나 인력 성과에 잘못 사용할 수 있다. 화면 툴팁, 지표정의서, CSV 메타정보가 필요하다.

### 9.3 점수가 성과평가로 오용될 가능성이 있다

장비 가중 점수는 업무량의 보조 지표일 뿐 검사 품질, 환자 난이도, 재검 여부, 교육 업무를 반영하지 않는다. 단독 인사평가 지표로 사용하면 잘못된 행동을 유도할 수 있다.

기획 문구에는 다음 원칙이 필요하다.

> 환산 점수는 장비별 업무량 비교를 위한 참고 지표이며 검사 품질 또는 개인 성과를 단독으로 평가하지 않습니다.

### 9.4 비활성 수집 버튼이 기대와 혼란을 만든다

사용자는 `오늘 수집`, `기간 수집`이 보이면 데이터가 갱신될 것으로 기대한다. 현재처럼 비활성 버튼을 노출하기보다 기능을 구현할 때까지 숨기거나 “관리자 기능·준비 중”을 명시해야 한다.

장기적으로 오늘 수집은 사용자가 누르는 기능보다 자동 스케줄러가 기본이어야 한다. 버튼은 관리자용 재시도 수단으로 두는 편이 제품 경험이 좋다.

### 9.5 조회 단위가 장비 탭에서는 실질적으로 작동하지 않는다

현재 월별·일별·주차별 선택은 `검사자 × 기간`의 컬럼 묶음에만 영향을 준다. `검사자 × 장비`에서는 선택을 바꿔도 같은 기간 전체를 합산하므로 화면이 달라지지 않는다.

선택지는 다음 중 하나로 정리해야 한다.

1. 조회 단위를 기간 탭에서만 표시한다.
2. 장비 탭에서는 “기간 합계”로 고정됐음을 표시한다.
3. 장비와 기간을 동시에 중첩하는 상세 피벗을 별도 제공한다.

### 9.6 클릭 가능한 행의 후속 행동이 없다

행에 포인터와 선택 색상이 있지만 상세 내역, 필터, 설명 패널이 열리지 않는다. 사용자는 드릴다운을 기대한다. 단순 선택이 필요 없다면 클릭 효과를 제거하고, 필요하다면 검사자 상세 패널을 연결해야 한다.

### 9.7 오류와 완료 피드백이 약하다

기간 검증 실패, 인증 실패, DB 연결 실패, 조회 시간 초과가 대부분 `연결 오류`로 보일 가능성이 크다. CSV 완료와 점수 적용 메시지도 눈에 잘 보이지 않는다. 사용자가 직접 해결할 수 있는 메시지와 재시도 동선이 필요하다.

### 9.8 첫 진입 기간이 고정되어 있다

초기값이 2026년 7월로 고정되어 있어 시간이 지나면 사용자가 매번 날짜를 바꿔야 한다. 데이터 시작일은 유지하되 기본 조회 기간은 최근 데이터가 있는 월 또는 현재 월로 계산하는 편이 자연스럽다.

## 11. 권장 개선 로드맵

### 1단계: 운영 안전성 확보

예상 범위: 1~3일

- `sa`를 SELECT 전용 계정으로 교체한다.
- 화면 상단에 마지막 수집 시각과 최신 원본 검사일을 표시한다.
- “검사 건수는 장비 검사 기록 수”라는 정의를 표시한다.
- 미구현 수집 버튼을 숨기거나 준비 중임을 명확히 한다.
- 프론트에서 최대 조회 기간과 미래 날짜를 검증한다.
- 오류 유형별 메시지를 구분한다.

완료 기준:

- 애플리케이션 계정으로 INSERT·UPDATE·DELETE가 불가능하다.
- 수집 지연 상태를 사용자가 화면에서 판단할 수 있다.
- 잘못된 기간 입력을 API 호출 전에 안내한다.

### 2단계: 레거시 운영 기능 대체

예상 범위: 1~2주

- 하루 단위 자동 수집 스케줄러를 구현한다.
- 기간 수집을 백그라운드 작업으로 구현한다.
- 수집 작업 ID, 진행률, 수신·신규·중복·실패 건수를 저장한다.
- 실패 일자만 재시도할 수 있게 한다.
- 점수 설정을 관리자 권한으로 저장하고 변경 이력을 남긴다.
- 조회 계정과 수집 계정을 분리한다.

완료 기준:

- 레거시 프로그램을 실행하지 않아도 신규 데이터가 자동 반영된다.
- 동일 기간을 반복 수집해도 중복이 발생하지 않는다.
- 장시간 기간 수집이 브라우저 종료와 무관하게 완료된다.
- 동일한 기간과 점수 버전은 모든 사용자에게 같은 결과를 제공한다.

### 3단계: 데이터 신뢰성과 확장성 강화

예상 범위: 2~4주

- 검사자·장비 ID 기반 집계로 전환한다.
- 점수 적용 기간과 버전을 도입한다.
- 서버가 필요한 피벗 단위로 집계하도록 API 옵션을 추가한다.
- 인덱스와 실행 계획을 점검하고 쿼리 제한시간을 설정한다.
- EOEIS 헬스체크, 응답시간, 오류율, 수집 지연을 모니터링한다.
- 검사자 행을 누르면 장비·일자 상세를 보는 드릴다운을 추가한다.

## 12. 최종 Go/No-Go 판단

### 읽기 전용 내부 파일럿

**조건부 Go**

조건은 다음과 같다.

1. `sa`를 읽기 전용 계정으로 교체한다.
2. 현재 데이터가 어떤 방식으로 수집되는지 운영 담당자를 지정한다.
3. 화면에 마지막 수집 시각과 검사 건수 정의를 표시한다.

### 레거시 프로그램 완전 종료

**현재 No-Go**

다음 기능이 준비되기 전에는 레거시를 종료하면 안 된다.

- 자동 증분 수집
- 기간 백필 및 실패 재처리
- 중복 방지 검증
- 점수 저장·권한·변경 이력
- 운영 모니터링과 장애 알림

## 13. 최종 평가

이 구현은 짧은 기간 안에 레거시 화면의 핵심 가치를 찾아 웹 대시보드로 옮긴 좋은 MVP다. 특히 실데이터 정합성, 개인정보 최소화, 피벗 전환, 넓은 테이블 사용성은 긍정적이다.

그러나 이 제품의 진짜 난이도는 화면이 아니라 **데이터가 매일 정확히 들어오고, 누가 점수를 바꿨는지 남고, 최소 권한으로 안전하게 운영되는가**에 있다. 현재는 “잘 조회되는 화면”까지 도달했고, 다음 단계는 “믿고 운영할 수 있는 시스템”을 만드는 것이다.

가장 먼저 해야 할 일은 UI 확장이 아니라 `sa` 제거, 데이터 최신성 표시, 수집 책임 확정이다. 이 세 가지를 해결하면 내부 조회 도구에서 운영 시스템으로 넘어갈 수 있다.

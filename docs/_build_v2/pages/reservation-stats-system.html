사용자와 쓰임새

예약 하나를 33칸으로 쪼갠 표

예약 종합이 "얼마나 왔나"라면 이 화면은 "각 채널이 어떤 과정을 거쳐 그만큼 만들었나"임. 인입콜 → 응대 → 신규문의 → 예약처럼 채널마다 중간 단계가 있고, 그 단계마다 비율이 붙음.

쓰는 장면하는 일
콜센터 성과응대율 · 신규문의 대비 예약율로 병목을 찾음
TM 성과총 DB · 유효 DB · 재상담까지 나눠 봄
온라인 채널네이버는 파트너거절을 빼고 유효접수 기준으로 봄
수치 보정시스템에 안 남는 값을 셀에 직접 입력함
이 표는 레거시 관리표를 옮긴 것임

인입콜 수·TM DB 수처럼 CRM 에 없는 값이 섞여 있음. 그래서 자동 집계만으로 채워지지 않고, 스냅샷(확정값) + 라이브(재조회값) 두 겹으로 관리함.

굵은 칸이 비율이고 화면에서 빨강으로 강조됨.

채널마다 '예약율'의 분모가 다름

인입콜은 인입콜 수, TM 은 총 DB, 네이버는 예약접수 대비임. 게다가 채널마다 보조 비율이 따로 있음 — 신규문의 대비 예약율, 유효 DB 예약율, 유효접수 예약율. "예약율"이라는 같은 이름이 여섯 번 나오므로 어느 그룹의 것인지 확인해야 함.

네이버는 파트너거절을 빼야 실제가 보임

네이버 예약접수에는 파트너가 거절한 건이 섞여 있음. 유효접수 = 예약접수 − 파트너거절이고, 유효접수 예약율이 실제 성과에 가까움.

스냅샷 + 라이브 두 겹

층내용
스냅샷(RSS)확정된 값. 사람이 고친 셀을 포함함
라이브지금 원천을 다시 조회한 값

둘이 갈라질 수 있어 진단 모달로 비교함. 이 화면이 신뢰를 유지하는 방식임.

왜 사람이 고칠 수 있어야 하나

인입콜 수·TM DB 수·카톡 문의 수는 CRM 에 남지 않음. 콜센터·TM·채팅 도구가 따로 있고 그 숫자는 담당자가 알고 있음. 자동 집계만으로는 표가 채워지지 않음.

데이터 소스

마트와 CRM 원천이 함께 잡힘 — 프로파일(postgres-mart / mssql)에 따라 갈리는 구조이거나, 공용 리포지터리를 거치며 다른 화면의 SQL 까지 딸려온 경우임. 어느 쪽이 실제 조회 경로인지는 확인이 필요함.

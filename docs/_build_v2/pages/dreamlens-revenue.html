사용자와 쓰임새

대시보드에서 유일하게 '입력하는' 원장

다른 화면은 CRM 을 읽어 보여주는데, 드림렌즈 장부는 이 화면이 원천임. 엑셀 시트로 관리하던 D/L 장부를 그대로 옮겨, 행 추가·수정·삭제를 화면에서 함.

쓰는 장면하는 일
렌즈 처방 기록고객·검사자·좌우 렌즈·색상·BOX 를 적음
매출 집계신규/재구매 · 보증금 · 피팅비 · 용품 · 진료비를 칸별로 넣음
리콜 관리1·2차 리콜 예약과 부재문자 발송 여부를 추적함
반납·반품좌우 각각 날짜를 남김
⚠️ 배치·마트를 타지 않음

dreamlens_ledger 테이블에 JPA 로 직접 CRUD 함. 스키마는 ddl-auto: update 가 만들고, 초기 10행은 시더가 표가 비었을 때만 넣음. CRM 에서 오는 값이 아니므로 지우면 복구할 원천이 없음.

표 · 지표 정의

그룹 6개

그룹칼럼비고
고객날짜 · 진료구분 · 고객번호 · 이름가로 스크롤 고정
기본 정보검사자 · 주소·구매구분제안 목록 있음
R 렌즈렌즈명 · BOX · R렌즈 · 색상 · 반납&반품날짜(R)좌우가 완전히 대칭임
L 렌즈렌즈명 · BOX · L렌즈 · 색상 · 반납&반품날짜(L)
매출D/L 신규 · D/L 재구매 · M 신규 · M FU 재구매 · H/L 신규 · H/L 재구매 · 보증금 · 피팅비 · 용품 · 진료비 · 렌즈 정가(참고)합계는 파생
리콜 관리다음예약 · 1차 리콜 · 1차 리콜예약 · 1차 부재문자 · 2차 리콜 · 2차 리콜예약 · 2차 부재문자후속 관리 축
매출 칸이 11개인 이유

렌즈 종류(D/L · M · H/L) × 신규/재구매 6칸 + 부대 수입 4칸 + 참고용 정가. 합계 하나로 받으면 어떤 매출인지 사라짐 — 시트가 칸을 나눠 쓰던 방식을 그대로 지켰음.

입력 상한

텍스트 칸의 길이 상한은 백엔드 @Size·엔티티 @Column(length) 와 같은 값을 화면에 둠. 화면에서 안 막으면 길게 붙여넣었을 때 DB 제약에 걸려 원인을 알 수 없는 실패로 보임.

화면에 B2B 매출 API 도 함께 잡힘

자동 추출된 API 목록에 /api/stats/b2b-revenue 가 섞여 있는데, 드림렌즈 장부 화면이 B2B 매출 컴포넌트와 코드를 공유하기 때문임. 장부 자체는 /api/dreamlens-ledger 만 씀.

0. TL;DR

  • 홈페이지 온라인 예약 데이터는 대시보드 DB(Postgres·MSSQL)와 다른 시스템(레거시 홈페이지 MariaDB bseyecom_db.TBL_COUNSEL).
  • 소스 지정: HOMEPAGE_DATASOURCE_URL 하나로 SQLite 스냅샷 / MariaDB 직결을 URL 접두사로 자동 스위칭.
  • 현재는 배치가 MariaDB 를 읽어 mart_list_reservation_homepage 에 적재하고, 앱은 마트를 조회한다. 조회 시점 원본 직결은 더 이상 표준 경로가 아니다.
  • 커밋 저자의 판단대로 됐다: "실증용. 운영 실시간이 필요하면 마트 ETL 쪽이 맞다."

1. 대상 시스템

  • 종류: MariaDB (레거시 PHP 홈페이지 bnviit-homepage-admin-rebuild 의 운영 DB)
  • 호스트: 192.168.200.32:3306 (내부망)

2-3. 설계 결정

결정 1. URL 접두사가 방언·드라이버·live 여부를 모두 결정한다

  • 별도 legacy.dialect 설정 키를 두지 않는다. jdbc:mariadb + dialect=sqlite 같은 모순 조합을 만들 여지를 없앤다.
  • 미지 접두사는 SQLITE 로 폴백 (실시간으로 오인해 경고를 끄는 것보다 안전).

결정 2. SQL 을 방언별 두 세트로 분리한다

  • 캐시가 원본을 snake_case 로 개명해 적재했기 때문(C_NO→legacy_no, M_NM→name, DIVICE_TYPE→device_type 등).
  • 스냅샷 SQL 을 원본 DB 에 그대로 쓰면 no such column 이 난다.
  • 결과 별칭 계약(14개)은 양쪽이 동일해야 하며 ReservationListHomepageSqlResourceTest 가 강제.

결정 3. LEGACY_DATASOURCE_URL 이 비면 관련 빈이 통째로 안 뜬다

  • @ConditionalOnProperty 대신 SpEL @ConditionalOnExpression("!'${legacy.datasource.url:}'.trim().isEmpty()") 사용.
  • @ConditionalOnProperty 는 빈 문자열도 "존재함"으로 봐서 500 이 남 → SpEL 로 공백까지 꺼짐 처리.
  • 결과: URL 비어 있으면 /api/reservation-list-homepage 만 503, 앱은 정상 기동.

결정 4. live 플래그로 프론트 경고 배너 자동 억제

  • 스냅샷 모드: lastRegDate 는 "이 시점 이후는 조용히 빈다" 라는 천장 → 조회 기간이 그 이후면 경고 배너.
  • 실시간 모드: lastRegDate 는 그냥 최근 등록건 시각 → 미래 조회할 때마다 거짓 경고 나오지 않도록 live=true 응답으로 배너 자동 억제, 대신 신선도 표시.

결정 5. 명명 정리 — snapshotMaxRegDate → lastRegDate

  • 실시간에서는 "스냅샷"이 아니라 이름이 사실과 어긋난다. DTO·zod·훅·페이지·SQL 별칭·SQL 파일명 일괄 정리.

결정 6. MariaDB 타입 함정 처리

  • C_NO int → CAST(C_NO AS CHAR) — 프론트 zod가 z.string() 강제.
  • REG_DATE datetime → DATE_FORMAT(..., '%Y-%m-%d %H:%i:%s') — 없이 두면 JDBC가 Timestamp 를 올려 zod 파싱 깨짐.

2-4. 회귀 검증

기준값: from=2026-06-01 / to=2026-06-30 → 206건. 운영 화면 동일 조건과 같은 값이다.

  • 소스가 SQLite → MariaDB 로 바뀌어도 206 으로 동일했다(SQL 재작성이 정확하다는 증거).
  • 2026-07-11 ~ 2026-07-15 → 34건. 스냅샷이면 0건인 구간 = 실시간 동작 증거 (스냅샷은 2026-07-10 16:15:55 고정).
  • 응답 계약: {rows, lastRegDate, live} · live=true · lastRegDate=2026-07-15 15:22:57.

숫자가 틀리면 아래를 의심할 것 — 증상별로 원인이 갈린다.

2-5. 알려진 한계 — 커밋 저자 명시

인용 (b61ff05 커밋 메시지):

터널 구성(사이드카)은 docker-compose.override.yml(gitignored)에 있다. 로컬 실증용이며 운영에 이 구조를 쓰지 말 것 — 터널이 끊기면 이 메뉴만 503 이고 상시성 보장 주체가 없다. 운영 실시간이 필요하면 마트 ETL 쪽이 맞다. H2 콘솔이 켜져 있으면 레거시 DataSource 도 목록에 올라온다. 실시간 + H2 콘솔 ON 조합을 운영에 올리지 말 것.

2-6. ⚠️ DefaultDataSourceConfig — 지우지 말 것

common/config/DefaultDataSourceConfig.java 는 버그 수정이다. 없으면 H2 프로파일에서 기동이 깨진다.

  • 원래 H2(프로파일 미지정)에서는 Spring Boot 의 DataSourceAutoConfiguration 이 primary DataSource 를 만들어줬다.
  • 그 auto-config 는 @ConditionalOnMissingBean(DataSource.class) — DataSource 빈이 하나라도 생기면 통째로 물러난다.
  • 홈페이지 DataSource 가 켜지자 SQLite 가 유일한 DataSource 가 되어 JPA 가 그걸 집어들고 Unable to determine Dialect for SQLite 3.47 로 기동 실패했다.
  • 그래서 다른 두 프로파일(mssql/postgres-mart)과 동일하게 primary 를 명시했다.

2-7. 화면 — 레거시와 의도적으로 다르게 만든 부분

레거시 관리자 화면 counsel/online_list.php 를 조회 전용으로 이관하면서 바꾼 것:

항목결정
삭제·체크박스제외 — 조회 전용. 쓰기 액션은 옮기지 않았다
CSV 내보내기제공 — 다른 리스트 화면과 동일. 개인정보가 원문으로 나가는 점 유의
검색이름·휴대폰번호 통합 단일 입력. 레거시는 휴대폰 검색이 안 돼 운영 불편이 있었다
개인정보원문 그대로 표시(레거시 화면과 동일). 마스킹 안 함
스냅샷 경고 배너신규 추가 — 레거시엔 없다. 실시간 소스면 초록 "실시간" 표시로 대체

레거시 동작을 그대로 따른 부분 — 바꾸면 건수가 틀어진다:

  • del_tf='N' 하드코딩 — 삭제건(281건)은 조회 대상 아님
  • ORDER BY legacy_no DESC — 등록일이 아니라 PK 역순
  • No 는 총건수에서 1씩 감소하는 표시용 번호(저장값 아님, 식별자는 legacyNo)
  • 진료구분=1(59건)은 레거시에도 라벨이 없어 빈칸

⚠️ 스냅샷일 때 조용한 실패 주의 — 조회 기간이 스냅샷을 넘으면 에러 없이 건수가 모자라게 나온다. 화면이 lastRegDate 비교로 경고 배너를 띄운다. 이 동작을 지우지 말 것. 실시간에서는 천장이 없어 같은 비교가 거짓 경고가 되므로 live 플래그로만 끈다 — 배너 자체를 지우면 안 된다.

3-4. 결정 필요 사항

이관 실행 전 확정해야 하는 것들:

  1. 직결 지원을 제거할지 유지할지 — 마트만 남기고 SQLite/MariaDB 직결 코드는 지울지, 로컬 개발용으로 남길지.
  2. 배치 노드의 MariaDB 접근 경로 — 상시 SSH 터널이 없다면 배치 시점에만 터널 열기, 아니면 사내망 라우팅 요청.
  3. naver/kakao 도 마트로 옮길지 — 현재는 MSSQL 직결 유지 결정(D1). 홈페이지만 마트로 가면 되나, 아니면 세 채널 모두 마트로 통합할지.

5. 온라인 예약 공식 (2026-06~) — 이 소스를 쓰는 이유

구 2026-07-15-예약자리스트_홈페이지-추가.md §9 에서 옮겨왔다. 이 화면이 단순 조회용이 아니라 월간 레포트·예약 종합의 입력이라는 점이 핵심이다.

대상: report/monthly#c-reservation-online 차트.

2024·2025    : 온라인 = RESERVE_PATH ONLINE/APP(홈페이지) + NAVER(네이버)   ← 카카오 미포함 · V12 시드
2026-01 ~ 05 : V24 골든 시드 (담당자 확정값 — 배치 write 차단)
2026-06 ~    : 온라인 = 네이버(RSS 기준) + 카카오톡(해피톡) + 홈페이지(리스트 화면과 동일한 raw)
               종합   = 콜 + 새 온라인

2024·2025 는 안 건드린다(V12 시드 + min-year 가드). 2026-01~05 도 V24 골든 시드로 고정이라 이 5개월은 예약통계 셀 오버라이드가 예약 종합·월간 레포트에 반영되지 않는다. 2026-06 부터 정의가 바뀐다 — 연도 비교 시 주의.

5-2. 알아둘 것

  • 네이버 값은 기존 종합의 NAVER 집계와 일부러 다르다. RSS 는 취소를 빼고 정크필터를 안 쓴다. 두 화면(월간 레포트 / 예약통계_시력교정)이 같은 숫자를 말하게 하는 게 이 정의의 전제다. 맞추려 하지 말 것.
  • 카카오는 원래 의도적으로 빠져 있었다. 사유는 "레거시 RSS 가 월마다 포함/미포함이 들쭉날쭉"이었고, 이제 마트가 직접 계산하므로 포함한다. 영향은 월 9~16건(1~3%).
  • 백내장은 원래도 안 들어왔다. 종합/네이버는 RESERVE_FLAG='M'(시력교정)으로 이미 걸러진다. ※ 홈페이지 백내장은 2025-02 이후 0건이라 최근 구간에서 이 필터는 미상 코드 1 만 걸러낸다.
  • 온전히 담지 못한 달은 null — 0 으로 더하면 '조용히 작은 온라인 예약'이 된다. 판정(coverageMonth)은 소스와 무관하게 같다: 말일까지 담긴 달만 인정한다. 단 2026-07 부터 진행 중인 달은 부분값이라도 노출하도록 완화됐다(커밋 ceca8a0).
  • 차트 라벨 온라인 예약 (네이버·카카오·홈페이지) 는 2026-06 부터 사실이 된다. 24·25 구간엔 카카오가 없어 라벨이 여전히 부정확하다 — 정의 전환 시점 표기를 붙일지 검토 필요.

5-3. 2026-07-24 이력

  1. 홈페이지 몫을 exam_type='5' + COUNT(DISTINCT phone) 에서 리스트 화면과 동일한 raw (전 진료 · COUNT(*)) 로 통일 — 예약 종합·월간 레포트·예약자 리스트_홈페이지 세 화면이 같은 홈페이지 건수를 참조하도록 정합.
  2. 오전에 컷오버를 2026-06 → 2026-01 로 앞당겼다가, 오후에 다시 2026-06 으로 복원. 2026-01~05 는 V24 골든 시드로 못 박기로 결정.

5-4. 반영 절차 · 검증 한계

공식만 고쳐선 값이 안 바뀐다. 배치를 2026 구간에 재실행해야 마트가 갱신된다 (BatchAdminController / ReservationReconcileService). 읽기 SQL·DDL 은 변경 없음.

⚠️ 네이버·카카오 실측 미완. SQL 형태와 합산 규칙만 테스트로 고정돼 있다 (ReservationOverallSqlResourceTest, ReservationOverallStatsServiceTest). 홈페이지 월별 값만 실측했다(2026-06 → 202건). MSSQL 접속은 가능하므로 monthly-naver.sql·monthly-kakao.sql 을 prod 에 직접 돌려 예약통계_시력교정 화면 수치와 대조할 수 있다. 공식 변경의 핵심인데 이 부분만 미검증이다.

6. FAQ

Q. MariaDB 직결이 이미 있는데 왜 마트로 또 가야 하나요? A. 커밋 저자가 실증용으로 명시한 상태입니다. 앱이 매 요청마다 SSH 터널로 원격 DB에 붙는 구조는 (1) 터널 상시성 부담, (2) 원본 DB에 부하 전가, (3) 다른 도메인(mart_reservation_overall_monthly 등)과 계산 축이 어긋남 문제가 있습니다. 마트로 가면 이 셋 다 해소됩니다.

Q. SQLite 스냅샷 방식은 왜 유지하고 있나요? A. 자격증명·터널 없이 동작해야 하는 환경(신규 개발자 온보딩, 오프라인 데모)이 있다는 것이 커밋 저자의 판단. 마트 이관이 완료되면 이것도 함께 제거 검토.

Q. 배치 이관하면 실시간성이 사라지는 것 아닌가요? A. 네. 다만 이 화면은 등록일 기준 조회이고 T-1 신선도로도 실무 요구는 충족한다는 것이 대시보드의 기본 정책(strategy.md §2 결정 2 참조). 실시간이 반드시 필요한 특별 요건이 있다면 예외 처리 검토.

Q. DIVICE_TYPE 오타는 어디서 왔나요? A. 원본 TBL_COUNSEL 컬럼명이 오타 상태로 굳어 있습니다. 대시보드 코드에서 수정하면 원본 스키마와 어긋나므로 그대로 씁니다. 별칭 단계(AS deviceType)에서 사용자에게 보이는 이름은 정정됩니다.
